# 阶段七交付物：测试策略与质量保障

> 项目：轻量级 Windows 工具箱（WinTools）
> 阶段目标：把散落在各迭代的验收用例系统化，形成单元 / 集成 / 手动 / 兼容 / 新手验收的完整测试计划
> 状态：已定稿（用户已确认测试策略，2026-11-18）
> 日期：2026-11-18
> 上游依据：阶段二（30 条 AC 验收用例）、阶段三（架构）、阶段四（UI 规范 + 可用性方案）、阶段五（安全边界）、阶段六（DoD + 迭代计划）

---

## 1. 本阶段要做成什么、不做成什么

- ✅ 要做成：一套分层的测试策略、每个工具该测什么的清单、可勾选的手动测试清单、兼容性矩阵、新手可用性测试方案、缺陷分级与发布准入标准。
- ❌ 不做成：逐条测试代码的实现（测试在对应迭代中随手编写，本阶段只定"测什么、怎么测、何时算通过"）；不做性能测试（工具箱无长时运行场景）。
- 🎯 完成标志（对应路线图验收标准）：**核心逻辑有单元测试覆盖，发布前通过全平台兼容性冒烟测试，且无阻断级缺陷**。

### 为什么现在做

阶段二已经为 7 个工具写了 30 条 AC 用例，阶段六 DoD 又要求"每个工具配单元测试"。如果临到发布才想怎么测，容易出现三种问题：核心逻辑没测到、重复劳动、不知道"测到什么程度能发布"。本阶段把这些提前定成规则，让每个迭代的测试有据可依。

## 2. 测试策略总览：测试金字塔

测试不是一种，而是分层。下层测试快、稳、多；上层测试慢、脆、少。**越靠下越应该自动化，越靠上越依赖人工**。初学者常犯的错是只做最上层的"手动点点点"——累、易漏、改一次代码全部要重测。

```
        ╱╲        新手验收测试 (UAT)  —— 5 人，验证"好不好用"
       ╱  ╲       兼容性测试          —— Win10/11、路径、DPI、权限
      ╱────╲      手动功能测试         —— 30 条 AC 用例逐条勾选
     ╱      ╲     集成测试            —— 发现机制、设置持久化
    ╱────────╲    单元测试 (xUnit)     —— 核心逻辑 + 异常路径，自动运行
```

| 层级 | 测什么 | 谁执行 | 频率 | 自动化 |
|------|--------|--------|------|--------|
| 单元测试 | 纯逻辑函数（格式化、编解码、改名规则、哈希向量） | 开发者 | 每次编译/提交 | ✅ 完全自动 |
| 集成测试 | 模块协作（工具发现、设置读写、主程序加载） | 开发者 | 每个迭代末 | ✅ 可自动 |
| 手动功能测试 | 30 条 AC 用例（含界面交互、拖放、弹窗） | 开发者 | 每个工具完成时 | ❌ 手动勾选 |
| 兼容性测试 | 不同系统 / 路径 / DPI / 权限下的冒烟 | 开发者 | 发布前 | 半自动 |
| 新手验收测试 | 新手能否独立、快速完成核心操作 | 真实新手 | 发布候选版 | ❌ 人工观察 |

**核心原则**：能在单元测试里验证的，绝不留到手动测试。这也是阶段三"逻辑与界面分离"架构的收益之一——逻辑纯净才能被单测。

## 3. 单元测试策略（xUnit）

### 3.1 测什么、不测什么

- ✅ **测**：可提纯为函数的业务逻辑——JSON 格式化/校验、Base64 编解码、密码生成规则、哈希算法、改名规则引擎、端口范围校验、容错包装。
- ❌ **不测**：WinForms 控件本身、拖放手势、弹窗样式（这些交给手动测试）；.NET 框架自带的类（如 `Convert.ToBase64String` 不必测，测你自己写的封装逻辑）。

### 3.2 测试工程结构

```
WinTools.sln
├── tests/
│   ├── WinTools.Core.Tests/        # 通用逻辑
│   └── WinTools.Tools.Tests/       # 各工具逻辑（按文件分）
│       ├── JsonToolTests.cs
│       ├── Base64ToolTests.cs
│       ├── PasswordToolTests.cs
│       ├── HashToolTests.cs
│       ├── RenameRuleTests.cs      # 重点
│       └── PortValidatorTests.cs
```

命名约定：`方法名_场景_预期结果`，例如 `Format_InvalidJson_ThrowsWithLineNumber`。这条约定让测试报告一眼可读。

### 3.3 每个工具的单元测试清单

> 这些是"单元级"补充，与阶段二的 AC 用例（偏端到端）互补。每条对应一个可断言的纯函数测试。

**T1 JSON 格式化/校验**
- `Format_ValidNestedJson_ReturnsIndented` —— 合法嵌套 JSON 输出正确缩进。
- `Format_MissingBracket_ThrowsWithLineNumber` —— 语法错误带行号信息。
- `Format_EmptyInput_ReturnsFriendlyMessage` —— 空输入不抛裸异常。
- `Format_ChineseContent_PreservesCharacters` —— 中文不乱码。

**T2 Base64 编解码**
- `Encode_Text_MatchesFrameworkResult` —— 与 `Convert.ToBase64String` 结果一致。
- `Decode_ValidBase64_RestoresOriginal` —— 合法串正确还原。
- `RoundTrip_ChineseText_IsIdentical` —— 中文编码→解码完全一致。
- `Decode_InvalidInput_ReturnsFriendlyMessage` —— 非法串不崩溃。

**T4 随机密码生成**
- `Generate_DefaultLength_MeetsRequirement` —— 默认长度/复杂度达标。
- `Generate_16CharsAllSets_MeetsAllFlags` —— 指定参数满足全部勾选条件。
- `Generate_TenTimes_NoDuplicateAndInCharset` —— 10 次无重复，字符都在选定集内（用多次采样 + 集合校验，避免偶发断言）。
- `Generate_UsesCryptoRng` —— 代码审查确认使用 `RandomNumberGenerator` 而非 `Random`（安全要求，阶段五）。

**F1 哈希校验**
- `Hash_KnownVectors_MatchExpected` —— 用标准测试向量断言：空文件、`abc`、`quick brown fox` 的 MD5/SHA1/SHA256 已知值（不依赖 `certutil`，测试内自包含）。
- `Hash_LargeFile_Streaming` —— 用生成的临时大文件走流式路径，验证分块读取逻辑正确。
- `Hash_LockedFile_ReportsError` —— 模拟读取失败，返回错误而非抛出。

**F2 批量重命名规则引擎（重点，唯一写操作）**
- `Plan_FiveFilesWithPrefix_ProducesExpectedNames` —— 序号规则生成正确的"原名→新名"计划。
- `Plan_IllegalChars_AreFiltered` —— `\ / : * ? " < > |` 全部被过滤。
- `Plan_NameCollision_AutoDisambiguates` —— 与现有文件重名时自动加序号，绝不返回覆盖计划。
- `Plan_ExtensionAlwaysPreserved` —— 任何规则下扩展名不变。
- `Undo_RestoresOriginalNames` —— 撤销栈能精确恢复原名。

**S2 端口校验**
- `Validate_PortOutOfRange_ReturnsFalse` —— 99999、0、负数、非数字均判非法。
- `Validate_PortInRange_ReturnsTrue` —— 1、80、65535 判合法。

**S1 系统信息容错**
- `Read_WhenFieldThrows_MarksUnavailable` —— 注入一个"读取失败"的模拟源，验证该项标记"不可用"且其余字段正常（容错逻辑需可注入，呼应阶段六"每个字段独立 try-catch"）。

### 3.4 覆盖率目标（务实版）

- **核心逻辑**（F2 规则引擎、T1/T2 编解码、哈希）：分支覆盖率目标 **≥ 70%**，且异常路径必须覆盖。
- **工具整体**：不设强制数字——WinForms UI 代码强求覆盖率性价比低。
- 覆盖率只作参考指标，**不以数字代替断言质量**：10 个有效断言胜过 100 个凑数测试。

## 4. 集成测试策略

单元测试验证"零件"，集成测试验证"装起来能转"。本项目三处最值得做集成测试：

| # | 测试点 | 验证方法 | 对应阶段 |
|---|--------|---------|---------|
| 1 | 工具自动发现 | 放入一个 `WinTools.Tools.*.dll` → 启动程序 → 导航出现该项；删除 DLL → 重启 → 该项消失。做成自动化脚本 | 阶段三架构目标 |
| 2 | 设置持久化 | 修改主题/窗口位置 → 关闭 → 重启 → 设置正确读回 | 阶段四通用能力 |
| 3 | 全工具加载无异常 | 启动程序 → 逐一点击 7 个工具 → 无崩溃、无未处理异常日志 | 阶段六 DoD |

> 第 1 项是阶段三"新增工具不改宿主核心代码"验收标准的自动化版本——它同时守护架构不退化。

## 5. 手动功能测试清单（30 条 AC 用例）

- [ ] **F1-AC3** >500MB 文件显示进度、界面不假死、结果正确

- [ ] **T4-AC2** 长度 16 + 勾选全部字符集 → 结果满足所有条件

## 6. 兼容性测试矩阵（发布前冒烟）

> 目标不是穷举，而是覆盖"最容易出问题的组合"。每一项跑一遍核心冒烟流程：启动 → 打开 T1 → 格式化一段中文 JSON → 打开 F1 → 校验一个小文件。

| 维度 | 测试组合 | 关注点 |
|------|---------|--------|
| **操作系统** | Win10 21H2、Win10 22H2、Win11 23H2 | 能否启动、.NET 10 运行时是否随包携带 |
| **路径** | 纯英文、含中文、含空格、深层长路径 | 文件读写、拖放是否失败 |
| **DPI / 缩放** | 100%、125%、150%、200%；多显示器不同缩放 | 界面模糊、控件重叠、文字截断 |
| **权限** | 标准用户（非管理员）全程 | 7 个工具全部可用、无 UAC 弹窗 |
| **区域语言** | 中文系统、英文系统区域设置 | 中文不乱码、日期/数字格式正常 |
| **干净环境** | 未装 Visual Studio / .NET SDK 的裸机 | `dotnet publish` 单文件能否独立运行 |

**执行策略**：至少覆盖 Win10 + Win11 各一台；路径和 DPI 用一台机器的不同设置组合验证；"干净环境"用虚拟机或临时用户账户模拟。结果填入兼容性矩阵表，逐项签字。

## 7. 新手可用性测试（UAT）

> 来源：阶段四"5 名新手 60 秒测试"方案。目的是验证"好不好用"，而非"对不对"——功能正确由前面的测试保证。

### 7.1 测试方法

- **对象**：5 名不熟悉本工具箱的人（家人、同事均可，无需技术背景）。
- **方式**：只给一句任务说明，**不提前教、不中途提示**，在旁观察并记录。
- **计时**：从打开程序到完成任务。

### 7.2 测试任务

1. **任务一（JSON 工具）**："请把这段乱糟糟的文字整理成好看的格式。"（给一段未格式化 JSON）
2. **任务二（哈希工具）**："请算出这个文件的校验码，并复制出来。"（给一个小文件）

### 7.3 记录指标

| 指标 | 记录方式 | 通过标准 |
|------|---------|---------|
| 完成率 | 60 秒内独立完成任务的人数 | ≥ 4/5 |
| 卡点 | 在哪一步停顿、误点、求助 | 无"找不到入口"类卡点 |
| 报错理解 | 遇到错误提示能否看懂下一步 | 至少 4 人能自行纠正 |
| 主观感受 | 一句话评价 | 无"太复杂/看不懂"的强烈负面 |

若某项不达标，回到阶段四的界面规范修正，而不是改测试标准。

## 8. 缺陷管理

### 8.1 严重级别定义

| 级别 | 定义 | 示例 | 处理要求 |
|------|------|------|---------|
| **阻断 (Critical)** | 程序崩溃、数据丢失、无法启动 | F2 静默覆盖了原文件；启动即闪退 | 立即修复，阻断发布 |
| **严重 (Major)** | 核心功能不可用或结果错误 | 哈希值与系统命令不符；中文乱码 | 发布前必须修复 |
| **一般 (Minor)** | 功能可用但有明显瑕疵 | 进度条偶发跳动；提示文案不清 | 排期修复，可带病发布 |
| **轻微 (Trivial)** | 不影响使用的细节 | 按钮对齐差 2 像素；拼写小错 | 有空再改 |

### 8.2 缺陷记录字段

`编号 / 级别 / 所在工具 / 复现步骤 / 预期 vs 实际 / 环境（系统+DPI+权限）/ 状态`

初学者可用 GitHub Issues 或一张简单的表格跟踪，关键是**每条缺陷都能被别人照着复现**。

## 9. 发布准入标准（Exit Criteria）

一个版本只有**全部满足**以下条件才算"可以发布"——这是阶段七验收标准的落地，也是进入阶段八的门槛：

- [ ] 阶段二 **30 条 AC 用例全部通过**，结果已记录。
- [ ] 核心逻辑单元测试通过率 100%，覆盖率达到第 3.4 节目标。
- [ ] 集成测试 3 项全部通过（尤其工具发现机制）。
- [ ] 兼容性矩阵核心组合全部通过冒烟。
- [ ] 无 **阻断** 与 **严重** 级缺陷。
- [ ] UAT 完成率 ≥ 4/5，无"找不到入口"类卡点。
- [ ] 依赖漏洞扫描 `dotnet list package --vulnerable` 无高危项（阶段五要求）。
- [ ] 7 个工具的报错样式与阶段四规范一致（一致性检查）。

## 10. 测试环境与工具

| 用途 | 工具 | 说明 |
|------|------|------|
| 单元测试 | xUnit + xUnit.runner.visualstudio | 随测试项目通过 NuGet 安装，VS 测试资源管理器直接运行 |
| 断言 | FluentAssertions（可选） | 让断言更易读，初学者可先用 xUnit 原生 `Assert` |
| 覆盖率 | Coverlet（可选） | `dotnet test /p:CollectCoverage=true`，VS 企业版自带覆盖率工具 |
| 哈希基准值 | `certutil -hashfile <文件> SHA256` | 手动核对 F1 的地面真相 |
| 端口占用基准 | `netstat -ano` / 资源监视器 | 手动核对 S2 结果 |
| 干净环境 | Windows 虚拟机 / 新建本地账户 | 验证免 SDK 运行与标准用户权限 |
| 缺陷跟踪 | GitHub Issues / 简单表格 | 关键是记录完整复现步骤 |
| 依赖扫描 | `dotnet list package --vulnerable` | 发布前必跑 |

## 11. 测试节奏（融入迭代）

测试不是独立阶段一次做完，而是**贯穿每个迭代**：

| 时机 | 做什么 |
|------|--------|
| 写工具时 | 同步编写单元测试（红灯→绿灯） |
| 工具完成时 | 跑该工具单元测试 + 勾选其 AC 用例 + 安全项检查（DoD 全 7 项） |
| 每个迭代末 | 集成测试（发现机制、全工具加载） |
| v1.0-rc（迭代 6） | 完整兼容性矩阵 + UAT + 一致性检查 + 漏洞扫描 |
| 发布前 | 对照第 9 节准入标准逐项签字 |
