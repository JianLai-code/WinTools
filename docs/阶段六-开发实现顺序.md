## 2. 核心策略：垂直切片 + 技术风险递增

### 2.1 什么是垂直切片

传统做法是先写所有接口、再写所有界面、最后接所有逻辑——初学者常因此卡在"永远跑不起来"。垂直切片反过来：**每次让一个工具从界面到逻辑到测试到可运行全部打通**。第一个切片最慢（要趟平所有坑），之后越来越快。

### 2.2 为什么按技术风险递增排序

把"技术不确定性最高"的工具放前面会在起步阶段连遭挫折。按依赖的技术类型从易到难递增：

```
纯内存计算  →  文件只读  →  系统只读  →  文件写入
 (T1/T2/T4)   (F1)      (S1/S2)      (F2 最复杂)
```

- 纯内存工具：无 IO、无权限、无状态，最适合练手打通全链路。
- 文件只读：引入拖放、大文件进度，但不改用户数据。
- 系统只读：引入 WMI/系统 API，容错要求高。
- 文件写入（F2）：唯一会改用户文件的工具，涉及预览、二次确认、撤销、防覆盖——风险最高，放最后，此时你已熟练。

### 2.3 与阶段二批次 A/B 的关系（重要澄清）

- **批次 A/B 是"范围优先级"**：决定工期不足时先砍谁（B 批 T2/T4 可延后）。
- **本迭代顺序是"实现顺序"**：决定先写谁，按技术难度排。

二者不矛盾。T2/T4 虽属 B 批，但与 T1 同属纯内存类、成本极低，顺手在第 2 个迭代一起做掉，几乎不增加工作量；即便砍掉也不影响主干。**7 个工具一个不少，只是换了下手顺序。**

## 3. 通用完成定义（DoD）

每个工具只有全部满足以下条件才算"完成"，这是防止"半成品堆积"的硬标准：

| # | 维度 | 完成标准 |
|---|------|---------|
| 1 | 接口 | 实现 `ITool`，标注 `[Tool]`，能被反射发现并出现在导航中 |
| 2 | 界面 | 遵循阶段四规范：统一按钮/输入/结果/报错，五步交互流程 |
| 3 | 功能 | 通过阶段二为其定义的全部验收用例（AC） |
| 4 | 测试 | xUnit 单元测试覆盖核心逻辑 + 异常路径；相关用例可自动运行 |
| 5 | 安全 | 符合阶段五：普通权限、不静默覆盖、日志脱敏（如适用） |
| 6 | 可运行 | 能从主程序点击进入、完整操作一遍、结果符合预期 |
| 7 | 记录 | 在 backlog 中标记完成，附上验收用例执行结果 |

## 5. 各迭代详细展开

### 迭代 0：地基（打通架构）

- **目标**：验证阶段三架构可行——空工具能被自动发现，宿主代码零改动。
- **内容**：
  1. 安装环境：Visual Studio 2022（含 .NET 桌面开发负载）、.NET 10 SDK、Git。
  2. 建解决方案 `WinTools.sln` 与项目：Core、Services、Shell、Tools.Hello。
  3. 实现 `ITool`、`ToolAttribute`（阶段三代码）。
  4. 实现 Shell 主窗口骨架：左侧导航 + 内容区 + `ToolDiscovery`（阶段三代码）。
  5. 实现空工具 `HelloTool`（阶段三代码）。
- **交付物**：可运行的空壳；导航显示"示例工具"，点击显示提示文字。
- **验收**：执行阶段三的"空工具验证四步骤"，特别是第 4 步（删 DLL 后宿主源码不改、导航项消失）。
- **关键决策**：此迭代不碰任何真实业务逻辑，只求跑通。

### 迭代 1：第一个垂直切片（T1 JSON 格式化）

- **目标**：趟平"接口→UI→逻辑→单测→发现→可运行"的完整链路，为后续建立模板。
- **内容**：新建 `WinTools.Tools.Text` 项目；实现 JSON 格式化/校验工具；用 `System.Text.Json`；配套 xUnit 测试。
- **验收用例**：T1-AC1 ~ AC4（阶段二）。
- **交付物**：导航出现"JSON 格式化"，可粘贴、格式化、报错提示、复制。
- **副产品**：把这次趟平的过程写成一份"新增工具标准操作手册"，后续迭代照抄。

### 迭代 2：文本小批量（T2 Base64、T4 随机密码）

- **目标**：复用迭代 1 的模板，快速积累同类工具，验证模板可复制。
- **内容**：在同项目新增两个工具类；T4 用 `RandomNumberGenerator`（阶段五安全要求）。
- **验收用例**：T2-AC1 ~ AC4、T4-AC1 ~ AC4。
- **交付物**：文本与编码类工具集（3 个工具）。
- **复用点**：结果区、复制按钮、错误提示全部沿用迭代 1 的控件。

### 迭代 3：文件只读（F1 哈希校验）

- **目标**：引入文件 IO 与异步处理，且不卡界面。
- **内容**：实现拖放区；用 `SHA256`/`MD5`/`SHA1` 类计算；大文件用异步 + 进度条（阶段四要求）；多文件逐行展示。
- **验收用例**：F1-AC1 ~ AC5（含大文件不假死、被占用文件优雅跳过）。
- **交付物**：可拖入文件并看到三种哈希值的工具。
- **技术要点**：用 `Task` + `IProgress<T>`，避免 UI 线程阻塞。

### 迭代 4：系统只读（S1 系统信息、S2 端口查询）

- **目标**：引入系统 API 读取，重点练"容错"——某项读不到不能崩溃。
- **内容**：S1 用 WMI/环境 API 读 CPU/内存/系统/磁盘；S2 用 `System.Net.NetworkInformation` 查本机连接表。
- **验收用例**：S1-AC1 ~ AC4、S2-AC1 ~ AC4（含普通权限可查、非法端口校验）。
- **交付物**：系统类工具集。
- **技术要点**：每个字段独立 try-catch，失败显示"不可用"。

### 迭代 5：文件写入（F2 批量重命名）

- **目标**：完成唯一会改用户文件的工具，把安全设计（阶段五）真正落地。
- **内容**：规则引擎（序号/替换）、改名预览表、危险按钮二次确认、冲突自动避让、撤销栈。
- **验收用例**：F2-AC1 ~ AC5（含绝不静默覆盖、非法字符过滤、可撤销）。
- **交付物**：完整可用的批量重命名工具——**此时 7 个 MVP 工具全部完成**。
- **技术要点**：先生成"改名计划"再执行；执行前复查目标文件是否存在。

### 迭代 6：打磨与发布预演

- **目标**：从"能用"到"可发布"。
- **内容**：
  1. 一致性检查：7 个工具的报错样式、按钮、结果区逐项比对阶段四规范。
  2. 可用性测试：按阶段四方案找 5 人做 60 秒测试。
  3. 修复测试暴露的问题。
  4. 打包预演：用 `dotnet publish` 生成单文件，验证在干净环境能运行（正式安装包在阶段八）。
  5. 依赖漏洞扫描：`dotnet list package --vulnerable`（阶段五要求）。
- **交付物**：发布候选版（Release Candidate）。
- **验收**：阶段六总验收——每个迭代都有可运行增量，且最终增量包含全部 7 个工具。
