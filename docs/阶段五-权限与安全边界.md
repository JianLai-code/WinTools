## 2. 最小权限原则

### 2.1 核心约定

- 主程序清单（app.manifest）设为 `asInvoker`：**跟随启动者的权限运行，绝不默认请求管理员**。
- 首版 7 个工具**全部为普通权限**——这是阶段一 D5（管理员工具二期再说）的直接落实。
- 不写系统目录（System32 等），不改注册表敏感项，不安装服务/驱动。
- 文件操作只碰用户**显式选择**的路径；工具箱自身的配置写入用户目录（`%LOCALAPPDATA%\WinTools\`）。

### 2.2 app.manifest 关键配置

```xml
<requestedPrivileges xmlns="urn:schemas-microsoft-com:asm.v3">
  <!-- 普通权限启动，避免首版任何 UAC 弹窗 -->
  <requestedExecutionLevel level="asInvoker" uiAccess="false" />
</requestedPrivileges>
```

> 注意：`asInvoker` 不等于"永远无 UAC"。如果用户本身用管理员账号登录，进程仍继承管理员令牌——因此工具内部仍要按 2.3 自检，不依赖"用户不是管理员"来保障安全。

### 2.3 路径与写入边界

| 允许 | 禁止 |
|------|------|
| 读写用户通过对话框选择的文件 | 静默读写系统目录 |
| 写 `%LOCALAPPDATA%\WinTools\`（配置、日志） | 写其他程序的安装目录 |
| 在用户选择的目录内创建新文件（重命名/转换结果） | 未经确认覆盖任何已存在文件 |

## 3. UAC 提权策略（为二期预留，首版不启用）

首版不提权，但架构要为二期的 hosts 编辑等工具留好路，避免到时候重构。

### 3.1 策略：整体不提权，按需提权

- ❌ 不采用"整个程序以管理员启动"——那会让所有工具都获得高权限，违反最小权限。
- ✅ 采用**按需提权**：只在用户点某个敏感工具时，以 `runas` 动词单独拉起一个提权进程，处理完即退出。

```csharp
// 二期 hosts 编辑的提权调用示意（首版不实现）
var psi = new ProcessStartInfo(currentExe)
{
    Arguments = "--tool hosts",
    Verb = "runas",              // 触发 UAC，用户确认后才获得管理员权限
    UseShellExecute = true
};
Process.Start(psi);
```

### 3.2 提权进程的三条铁律

1. 只做被授权的那件事（改 hosts），不加载其他工具。
2. 修改前自动备份原文件，失败可回滚。
3. 用户拒绝 UAC 时，给出友好提示并安全退回，不反复弹窗。

## 5. 数据隐私边界

- **首版零联网**：7 个工具无任何网络请求。N2 公网 IP 等联网工具已排除（D3）。
- **不采集、不上报**：不收集文件路径、文件内容、使用频率、机器信息到任何服务器。
- **日志脱敏**：日志只记录操作类型与错误码，不记录文件完整路径、不记录文本内容（避免把用户隐私写进日志文件）。
- **本地存储**：配置与日志仅存 `%LOCALAPPDATA%\WinTools\`，卸载时随目录清理。
- **随机数安全**：密码生成器用 `RandomNumberGenerator`（密码学安全），不用普通 `Random`。

### 5.1 隐私说明（对外文案初稿，随发布页给出）

> WinTools 在您电脑上本地运行。首版不会连接互联网，不会收集或上传您的任何文件、数据或使用情况。所有处理均在您的设备内完成。

## 6. 依赖供应链安全

第三方 NuGet 包是主要攻击面，规则如下：

1. **只用可信来源**：优先 Microsoft 官方包；第三方包需确认维护活跃、来源可靠。
2. **固定版本**：不用浮动版本号（`*` 或 `[1.0,)`），每个包锁定精确版本。
3. **启用锁文件**：提交 `packages.lock.json`，确保构建可复现、防止依赖被悄悄替换。
4. **定期漏洞扫描**：每版发布前运行 `dotnet list package --vulnerable`，无高危漏洞才发。
5. **最小依赖**：能用 .NET 内置 API 解决的（如 JSON、Base64、哈希）绝不引第三方包——本 MVP 7 个工具预期零第三方运行时依赖。

## 7. 更新安全

首版不做自动更新（保持简单），但为阶段九的更新器定好安全规则：

- **仅 HTTPS**：更新检查与下载只走 HTTPS，拒绝明文 HTTP。
- **签名校验**：更新包必须校验数字签名或至少比对官方发布的 SHA256 值，校验失败拒绝安装。
- **来源固定**：更新地址硬编码为官方域名，不从配置或第三方结果动态获取。
- **用户知情**：更新需用户确认，不静默下载安装。

## 8. 代码签名现实策略（重要修正）

### 8.1 必须纠正的过时认知

最初规划里写过"买代码签名证书即可消除 SmartScreen 警告"。查证微软官方文档后，这个说法**已过时**：

- **EV 证书自 2024 年起不再绕过 SmartScreen**——EV 与 OV 在新文件首次下载时表现相同：都会提示"应用未被识别"，但会显示已验证的发布者名称。为绕过警告而多花 EV 的钱已不值得。
- **声誉随时间和下载量积累**：即使签名，新文件初期仍可能警告，需要数周、数百次干净安装才逐步消失。没有手动加白名单的渠道（消费端）。
- **Windows 11 的 Smart App Control** 可能直接拦截未签名文件，比 SmartScreen 更严格。

### 8.2 各方案对比（2026 年现状）

| 方案 | 成本 | 首次下载警告 | 适用 |
|------|------|------------|------|
| Microsoft Store（MSIX） | 开发者账号费用 | ✅ 无（微软重新签名） | 最可靠，但有上架门槛 |
| Azure Artifact Signing | 约 $9.99/月 | ⚠ 初期有，声誉积累后消失 | **个人仅限美/加**；组织限美/加/欧/英 |
| OV 证书 | 约 $150–300/年 | ⚠ 同 Azure | 全球可用；需 HSM 硬件令牌 |
| EV 证书 | 约 $400+/年 | ⚠ 同 OV，不再有优势 | 仅企业采购场景有意义 |
| 自签名 | 免费 | ❌ 等同未签名 | 仅开发测试 |
| 不签名 | 免费 | ❌ 强警告，企业可能完全拦截 | 不推荐公开分发 |

### 8.3 对本项目（个人开发者、面向中文用户）的建议

- **阶段八首版**：先用自签名做本地/内测，明确告知内测用户首次会有警告；同时**每个版本都用同一签名身份**，为将来声誉积累打基础。
- **公开分发时**：由于 Azure Artifact Signing 个人仅限美/加，中国个人开发者的现实选择是 ① 购买 OV 证书（需硬件令牌，约 $150–300/年），或 ② 上架 Microsoft Store（MSIX）以获得无警告体验。
- **不要为绕 SmartScreen 买 EV**——多花钱无收益。
- 无论哪种方式，都要在下载页明确写"发布者名称 + 官方来源"，让用户能自行核验。

> 这条修正会同步到阶段八的发布策略中。
