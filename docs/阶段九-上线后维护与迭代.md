# 阶段九交付物：上线后维护与迭代

> 项目：轻量级 Windows 工具箱（WinTools）
> 阶段目标：建立长期稳定演进机制——能响应用户反馈、不破坏兼容性地持续发布小版本
> 状态：已定稿（用户已确认维护方案，选定"方案 A 手动检查更新"，2026-11-18）
> 日期：2026-11-18
> 上游依据：阶段一（范围边界）、阶段五（零联网与更新安全）、阶段七（缺陷分级）、阶段八（语义化版本 + CHANGELOG）

---

## 1. 本阶段要做成什么、不做成什么

- ✅ 要做成：语义化版本规范、反馈渠道、自动更新方案（含与零联网边界的取舍）、依赖定期维护机制、长期 backlog 管理、日常运维节奏、维护手册。
- ❌ 不做成：实际运营一个用户社区、搭建服务器后端（本项目是纯本地工具，无需后端）。
- 🎯 完成标志（对应路线图验收标准）：**能响应用户反馈并在不破坏兼容性的前提下持续发布小版本，用户可平滑升级**。

### 一个必须先讲的判断：自动更新 vs 零联网

最初规划要求"轻量自动更新"，但阶段五已把首版定为核心卖点——**零联网、零数据外传**。这两者天然冲突：自动更新必须联网。

**用户已决策：首版采用"方案 A 手动检查更新"，保住零联网卖点。** 理由：一个 7 工具的小工具箱，用户不会频繁检查更新；为了偶发的更新省几步点击，牺牲"绝不联网"的信任，不划算。下面第 4 节仍保留两个方案的完整设计——方案 A 为采纳方案，方案 B 作为未来用户规模上升后的可选储备（不纳入当前范围）。

## 2. 语义化版本规范（SemVer）

版本号格式 `主版本.次版本.补丁`（如 `1.2.3`），升级规则必须严格遵守，用户才能预期"这次升级会不会出问题"：

| 变更类型 | 升哪一位 | 示例 | 场景 |
|---------|---------|------|------|
| **不兼容的改动 / 架构重构** | 主版本 | 1.2.3 → 2.0.0 | 插件接口 `ITool` 大改、工具配置格式不兼容 |
| **新增功能（向后兼容）** | 次版本 | 1.2.3 → 1.3.0 | 新增一个工具、新增一个设置项 |
| **仅修复 bug（向后兼容）** | 补丁 | 1.2.3 → 1.2.4 | 修哈希算错、修界面错位 |

配套规则：
- **预发布版本**用 `1.3.0-rc.1`（发布候选）、`1.3.0-beta.1`（测试版）标识。
- 阶段八提到 **AppId GUID 一旦发布绝不改动**——否则系统识别为新软件，无法覆盖升级。
- 每个版本必须在 `CHANGELOG.md` 留记录（格式见阶段八第 8.2 节）。

## 3. 反馈渠道

### 3.1 渠道选择

| 渠道 | 收集什么 | 适合 | 成本 |
|------|---------|------|------|
| **GitHub Issues** | bug 报告、功能建议 | 开发者用户、公开透明 | 免费 |
| **内置"反馈"入口** | 跳转到 Issues / 邮箱 | 普通用户，藏在"关于"页 | 零联网（只打开浏览器） |
| **邮箱** | 私密反馈、附件截图 | 不习惯 GitHub 的用户 | 免费 |
| **应用内诊断日志** | 崩溃现场 | 定位疑难问题 | 需日志脱敏（阶段五） |

### 3.2 反馈处理流程

```
收到反馈 → 归类(bug/建议/咨询) → 复现确认 → 定级(沿用阶段七四级)
   → 进 backlog → 排期修复 → 测试验证(阶段七) → 发布 → 回复反馈人
```

**关键纪律**：
- 每条 bug 反馈都要**先复现再动手**——很多"bug"是环境差异或误操作。
- 复现不了的要记录环境信息（系统版本、DPI、权限、步骤）并恳请补充，不要直接关闭。
- 修复后**回到阶段七跑测试**，不能因为改动小就跳过——这是"不破坏兼容性"的保障。
- 反馈人要能收到"已修复"的回复，形成正循环。

## 4. 更新机制：两个方案（已选定方案 A）

### 方案 A：手动检查更新（推荐，保住零联网）

- **做法**：在"关于"页放一个"检查更新"按钮，点击后**才**打开浏览器跳转到 GitHub Releases 页面，用户自行下载安装。
- **联网时机**：仅用户主动点击时，且是打开系统浏览器，**程序本身从不联网**。
- **隐私**：完全保住"零联网、零数据外传"卖点。
- **成本**：极低（一个超链接），零安全风险。
- **适合**：首版、用户量小、重视信任的场景。

### 方案 B：可选自动更新模块（二期，需显式开启）

若未来用户规模上升、确有自动更新需求，按以下安全设计实现（严格遵守阶段五更新边界）：

```
检查更新(HTTPS) → 对比版本号 → 提示用户"发现新版本 v1.3.0"
   → 用户确认 → 下载到临时目录 → 校验数字签名/哈希
   → 再次确认 → 调用安装包静默安装 → 重启应用
```

**强制安全约束**（缺一不可，来自阶段五）：
1. **默认关闭**，首次使用需用户显式开启——不搞"默认联网偷偷检查"。
2. 全程 **HTTPS**，证书校验不可跳过。
3. 下载后**校验签名或官方哈希**，校验失败立即丢弃并告警。
4. **两次用户确认**：更新前确认、安装前确认，绝不静默安装。
5. 更新日志随包提供，让用户知道改了什么。
6. 提供**一键关闭**更新检查的开关。

> 两者不冲突：可以首版用方案 A，把方案 B 作为 v2.0 的可选功能，并在设置里给注重隐私的用户关闭开关。

## 5. 依赖与供应链维护

第三方依赖（NuGet 包、Inno Setup）是长期安全隐患的主要来源。建立定期维护节奏：

| 频率 | 动作 | 命令/方法 |
|------|------|----------|
| 每次发布前 | 漏洞扫描 | `dotnet list package --vulnerable` |
| 每季度 | 检查依赖更新 | `dotnet list package --outdated` |
| 每半年 | 检查 .NET LTS 支持状态 | 微软官方 .NET 支持策略页 |
| 依赖升级后 | 全量回归测试 | 阶段七测试计划 |

**原则**（呼应阶段五）：
- 依赖尽量少，能用框架自带类就不引第三方包。
- 升级依赖不是越多越好——只升必要的安全补丁，每次升级后必跑测试。
- 保留依赖清单和版本锁定（`packages.lock.json`），确保构建可复现。

## 6. 长期 Backlog 管理

阶段二排不进首版的候选工具、用户提的新需求，统一进 backlog，按"价值 × 成本"持续排序（沿用阶段二方法）。

### 6.1 Backlog 来源

- 阶段二候补池：F5 编码转换、T3 URL、T5 时间戳、S4 环境变量、I3 二维码、N1 Ping 等。
- 二期储备：F3 文件夹大小、T6 文本 Diff、I1/I2 图片类。
- 用户反馈的新需求。
- 开发者自己在使用过程中发现的痛点。

### 6.2 排序与节奏

- 每个大版本周期开始时，重新评估 backlog，挑出下一批"Must/Should"。
- 沿用 MoSCoW 分类和硬约束（新增工具仍需离线、普通权限，除非阶段五策略变更）。
- 新增工具严格走阶段六的 DoD 和"新增工具标准操作手册"——架构目标（零改宿主）要长期守护。

### 6.3 防范围蔓延

维护期最常见的失败是"什么都想加"，最终变成臃肿软件。守住阶段一的"不做什么"边界：
- 不做需管理员常驻、后台自启、账号云同步、自动删除文件的工具。
- 每个新工具都要回答"谁、什么场景、得到什么结果"，答不上来就不做。

## 7. 日常运维节奏

| 周期 | 固定动作 |
|------|---------|
| **每次改代码** | 跑单元测试（阶段七）；新增/改动工具走完整 DoD |
| **每次发版** | 过发布准入标准（阶段七第 9 节）→ CHANGELOG → 打包验证（阶段八）→ 发布 |
| **每月** | 浏览一遍反馈，归类处理；看一眼崩溃日志 |
| **每季度** | 依赖更新检查；回顾 backlog 排下一次迭代 |
| **每半年** | 核对 .NET 支持状态；检查签名证书是否到期（若已购 OV） |
| **每年** | 复盘产品方向：哪些工具高频用、哪些没人用（后者可在下个大版本移除） |

## 8. 维护手册（给未来自己的速查）

把最常查的操作集中在一处，建议建 `docs/维护手册.md`，至少包含：

1. **如何加一个新工具**——链接阶段六"新增工具标准操作手册"，三步：建项目 → 实现 `ITool` → 编译验证被发现。
2. **如何发一个小版本**——改版本号 → 更新 CHANGELOG → 跑准入标准 → `dotnet publish` → Inno Setup 编译 → 签名 → 全新机器验证 → 上传。
3. **如何回滚**——保留上一版安装包；发现严重 bug 时撤下问题版本、重新发布补丁版（补丁号 +1）。
4. **关键常量位置**——AppId GUID、签名证书路径、发布渠道地址、版本号定义处。
5. **故障排查**——工具不显示（查插件 DLL）、启动崩溃（看日志）、更新失败（查签名/网络）。
