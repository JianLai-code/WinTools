# 新增工具标准操作手册

> 用途：后续 6 个工具（T1/T2/T4/F1/S1/S2/F2）都照这份手册做，不用重新设计。
> 来源：阶段六迭代 1 要求把趟平的过程沉淀成模板；迭代 0 先给出可执行的骨架。
> 前置：已理解阶段三的 `ITool` 接口与发现机制。

---

## 核心原则

宿主（WinTools.Shell）**永远不用改**。新增工具全过程只跟新项目打交道，Shell 源码一行不动。如果你发现自己正在改 MainForm.cs 或 ToolDiscovery.cs 来"接入"新工具——停下来，方向错了。

架构之所以能做到这一点：Shell 运行时扫描 `WinTools.Tools.*.dll`，靠 `[Tool]` 特性 + 反射自动发现。`Directory.Build.props` 负责把工具 DLL 复制到 Shell 输出目录。

## 标准五步

### 第 1 步：建项目

在 `src/` 下新建类库项目，命名**必须以 `WinTools.Tools.` 开头**（发现器靠这个前缀识别）：

```bash
# 以文本工具为例，同一项目可放多个工具类
dotnet new classlib -n WinTools.Tools.Text -o src/WinTools.Tools.Text -f net10.0-windows
```

把生成的 `Class1.cs` 删掉。编辑 csproj 确认内容如下（关键是 `UseWindowsForms` 和 Core 引用）：

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0-windows</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <UseWindowsForms>true</UseWindowsForms>
  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="..\WinTools.Core\WinTools.Core.csproj" />
  </ItemGroup>
</Project>
```

把项目加入解决方案：

```bash
dotnet sln WinTools.sln add src/WinTools.Tools.Text/WinTools.Tools.Text.csproj
```

> 不需要手动配置 DLL 复制——`Directory.Build.props` 会自动把所有 `WinTools.Tools.*` 项目的产物复制到 Shell 目录。

### 第 2 步：实现 ITool（元数据 + 界面）

新建工具类，照抄 `HelloTool.cs` 的结构：

```csharp
using System.Windows.Forms;
using WinTools.Core;

namespace WinTools.Tools.Text;

[Tool(Order = 10)]   // Order 越小，导航越靠前
public sealed class JsonFormatterTool : ITool
{
    public string Id => "json-formatter";        // 全局唯一，小写英文+连字符
    public string Name => "JSON 格式化";
    public string Category => "文本工具";          // 同类工具用相同分类，会自动分组
    public System.Drawing.Icon? Icon => null;

    public Control CreateUI()
    {
        // 在这里构建并返回这个工具的主界面（WinForms 控件）。
        // 遵循阶段四规范：输入区 + 操作按钮 + 结果区 + 错误提示。
        var panel = new Panel { Dock = DockStyle.Fill };
        // ... 具体控件
        return panel;
    }
}
```

**元数据约定**（保持导航整洁）：
- `Id`：全局唯一，用"类名小写+连字符"，一经发布不要改（设置按 Id 存储）。
- `Category`：目前用「文本工具 / 文件工具 / 系统工具 / 其他」四类，与阶段四原型一致。
- `Order`：同类里按使用频率排，主推工具给小数值（如 10、20）。

### 第 3 步：写核心逻辑（放独立类，便于单测）

**关键**：不要把业务逻辑写进 `CreateUI` 的事件处理器里。把它抽成纯逻辑类，这样单元测试能直接测它——这是阶段七测试策略的前提。

```csharp
// JsonFormatter.cs —— 纯逻辑，无 UI 依赖
public static class JsonFormatter
{
    public static string Format(string input) { /* ... */ }
}
```

界面代码只负责：收集输入 → 调用逻辑类 → 显示结果 → 捕获异常显示错误提示。

### 第 4 步：写单元测试

在 `tests/WinTools.Tools.Tests/` 建对应测试类，覆盖正常输入 + 异常路径。用例来自阶段二该工具的 AC 用例 + 阶段七的单元测试清单。

```csharp
[Fact]
public void Format_InvalidJson_ReturnsFriendlyError()
{
    var result = JsonFormatter.Format("{ bad }");
    Assert.False(result.Success);
    Assert.Equal(string.Empty, result.Text); // 不输出半成品
}
```

> 完整范例见 `tests/WinTools.Tools.Tests/JsonFormatterTests.cs`（T1-AC1~AC4 全覆盖，可直接照抄结构）。

### 第 5 步：编译并验证自动发现

```bash
dotnet build WinTools.sln
```

验证清单（照阶段三"空工具验证四步骤"）：
- [ ] 编译成功，工具 DLL 出现在 Shell 的 `bin\Debug\net10.0-windows\` 目录。
- [ ] 启动 Shell，左侧导航出现新工具的「分类 → 名称」。
- [ ] 点击导航项，内容区显示工具界面。
- [ ] **反证**：删除该 DLL 后重启，导航项消失，而 Shell 源码一行未改。

## 常见坑位

| 现象 | 原因 | 解决 |
|------|------|------|
| 导航里没有新工具 | 项目名没以 `WinTools.Tools.` 开头 | 按约定重命名项目 |
| DLL 没复制到 Shell 目录 | `Directory.Build.props` 未生效 / 项目名不符 | 检查文件名与项目名；重新生成解决方案 |
| 编译报"找不到 ITool" | 忘了引用 Core 项目 | csproj 加 `ProjectReference` |
| 编译报"找不到 Control/Icon" | 忘了 `UseWindowsForms=true` | csproj 加上 |
| 工具点击就崩溃 | `CreateUI` 抛异常 | 检查构造逻辑；Shell 已有兜底会显示错误区，但应修根因 |
| 改了代码但界面没变 | 旧 DLL 还在 Shell 目录 | 清理后重新生成（`dotnet clean` 再 `build`） |
| 中文被转义成 `\u4E2D` | `System.Text.Json` 默认转义非 ASCII | 序列化选项加 `Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping`（T1-AC4） |
| 测试 DLL 被当成工具复制 | 测试项目名以 `WinTools.Tools.` 开头 | 保持测试项目名不带该前缀；发现器与复制规则已双重排除 `.Tests` |
| 新增工具发现不到（有多个工具时） | 独立加载上下文里 Core 被重复加载，类型不兼容 | `ToolDiscovery` 的 `Resolving` 回调复用默认上下文的已加载程序集（迭代 1 已修） |
| 编译报 CS0009/CS2012"文件被占用" | 杀毒软件实时扫描新 DLL（本机实测是 **360rp.exe**）/ 测试宿主残留句柄 | 报错信息会点名锁定进程（如"文件被 360rp.exe 锁定"）；最有效解法是**删掉该项目被锁的 `bin`/`obj` 目录后一次性重编译**，缩短杀软介入窗口：`rm -rf tests/<项目>/bin tests/<项目>/obj` 再 `dotnet test`；或 `dotnet build-server shutdown` 后关掉正在运行的 Shell.exe 再编译 |
| `File.WriteAllBytes` 报"命名空间中不存在该类型" | 新建的工具项目命名空间叫 `WinTools.Tools.File`，与 `System.IO.File` 类冲突——同在 `WinTools.Tools.*` 下时，`File` 优先解析成那个子命名空间 | **命名空间用复数 `WinTools.Tools.Files`，但项目名/程序集名保持 `WinTools.Tools.File`**（复制规则靠项目名前缀，发现靠 `[Tool]` 特性，都不依赖命名空间）。迭代 3 踩过 |
| xUnit 报"could not find dependent assembly"/"没有可用测试" | 360 锁定导致测试依赖没复制全 | 删掉测试项目 `bin`/`obj` 重新 `dotnet test`；不要盲目加 `--no-build` |
| 哈希测试断言大小写不符 | `Convert.ToHexString` 输出**大写**（与 certutil 一致），标准向量常写成小写 | 期望值统一 `.ToUpperInvariant()` 再比较；逻辑保持大写不改 |
| 项目名带 `.System` 导致命名空间冲突 | 命名空间若叫 `WinTools.Tools.System` 会和 BCL 的 `System` 根命名空间混淆 | 命名空间用 `WinTools.Tools.SystemTools`，项目名保持 `WinTools.Tools.System`（复制规则靠项目名） |
| 编译报 CS1002"应输入 ;"（中文文案那行） | 字符串内容里混进了 **ASCII 直引号**，提前终止了字符串 | 文案里的引号用中文书名号 `「」` 或全角引号；代码定界符才用 ASCII 直引号 |
| 编译报 CS0663"仅 out/ref 不同不能重载" | P/Invoke 方法 `GlobalMemoryStatusEx(ref X)` 与包装方法 `GlobalMemoryStatusEx(out X)` 同名 | 包装方法换个名字（如 `TryGetMemoryStatus`） |
| 编译报 CS0118"'Cursor' 是类型但用作变量" | 在 ITool 实现类的局部函数里写 `Cursor = ...`，被解析成 `System.Windows.Forms.Cursor` 类型 | 用具体控件 `.Cursor`，或直接不用等待光标 + `Application.DoEvents()` |


## 迭代 3 沉淀：文件类 + 异步工具的标准做法

F1 哈希是第一个"读写文件 + 异步"工具，以下做法可直接复用到迭代 4、5：

1. **一次读取，多路消费**：同时算 MD5/SHA1/SHA256 时，别读三遍文件。用三个 `IncrementalHash`，每次读到一块 `span` 就依次 `AppendData` 给三个实例——只读一遍磁盘，内存恒定。迭代 5 的文件操作也应避免整文件载入内存。

2. **异步 ≠ 在 UI 线程外碰控件**：`FileHasher.ComputeAsync` 是纯逻辑，不碰任何控件；进度通过 `IProgress<int>` 回传。`new Progress<int>(...)` 的回调**自动在 UI 线程执行**，可以安全地更新进度条/标签——这是 WinForms 异步的安全通道，不要图省事在后台线程直接改控件。

3. **被占用文件要能读**：`FileStream` 用 `FileShare.ReadWrite`（而非默认 `Read`），否则用户用 Word/记事本打开着的文件会读取失败。配合"每个文件 try-catch 转成结果对象"，做到一个失败不影响其他（F1-AC4）。

4. **大文件用 `ArrayPool<byte>`**：1MB 缓冲区若每次 `new` 会造成 GC 压力；用 `ArrayPool.Shared.Rent/Return` 复用。配合 `FileOptions.Asynchronous | SequentialScan` 提示系统优化顺序读。

5. **标准向量测试不要依赖外部命令**：`certutil` 在不同 Windows 版本输出格式/大小写可能不同，测试应自包含——硬编码公认向量（注意大写），或对大文件用 .NET 内置 `MD5.HashData` 等一次性 API 交叉验证。

## 迭代 4 沉淀：系统类工具的两个可测试设计

S1、S2 都是"读系统状态"的工具，这类工具的共性难题是**环境不可控、难以在测试里复现**。两个设计值得复用：

1. **可注入的容错（S1）**：把每个字段的读取做成 `Func<string>` 委托，通过 `CollectFrom(sources)` 注入。生产用 `Collect()` 传真实读取器；测试传入一个"会抛异常的委托"，就能稳定验证"该项标记不可用、其余正常"——不必真的去破坏系统配置。这是让"容错"这件事可自动化验证的关键，呼应阶段七 S1 单测要求。

2. **纯函数解析 + 薄封装（S2）**：端口查询依赖 `netstat` 这个外部命令，但它把"启动进程取输出"（`GetListeningPids`）和"解析文本"（`ParseListeners(string)`）拆开了。解析是纯函数，单测只要喂一段样例文本（英文格式、IPv6、中文 Windows 格式各一份），就能验证正确性，完全不依赖测试机上哪些端口正被占用。实际 netstat 输出格式已在本机核对（列顺序 fixed，LISTENING 关键字中英文一致）。

3. **零第三方依赖读系统信息**：CPU 从注册表 `HKLM\HARDWARE\DESCRIPTION\System\CentralProcessor\0` 读 `ProcessorNameString`；内存用 P/Invoke `GlobalMemoryStatusEx`；磁盘用 `DriveInfo`。全部只读、普通权限、无需 WMI 或 NuGet 包——符合阶段五"供应链最小化"。注意 `ulong` 字节数转 `long` 要显式转换，P/Invoke 包装方法别和原生方法同名（否则 out/ref 重载冲突）。

## 迭代 2 沉淀：一次流程验证，两个新经验

迭代 2 同时加了两个工具（T2 Base64、T4 密码），全程照抄迭代 1 建立的模板，没有再踩新的架构坑——这证明模板是可靠的。补充两条值得记住的经验：

1. **密码生成必须用密码学安全随机数**：`RandomNumberGenerator.GetInt32(n)` 而非 `Random`。`Random` 是可预测的（种子可推导），生成的密码不安全。这里用了一个源码审查测试（`Generate_SourceUsesCryptoRng_NotRandom`）来守护这条安全底线——它读取自己的源码，确认没有 `new Random(`。测试项目用 csproj 的 `Content` 项把源文件复制到输出目录，用 `AppContext.BaseDirectory` 定位，避免相对路径不稳定。
2. **"满足所有勾选条件"需要主动保证**：如果只从合并字符集里纯随机取字符，可能某种类型一个都没抽到（例如勾了数字但 16 位里没有数字）。做法是先从每个勾选的字符集各取一个字符，再补齐剩余，最后用 Fisher-Yates 洗牌打散顺序。这样既满足 AC2，又不失去随机性。

3. **构造测试用例时先核对基准串**：本轮一个测试失败是自己手误——把 Base64 基准串里的 `s` 写成了逗号，导致解码断言失败。教训：写编解码往返测试的常量时，用工具生成的准确值，不要手敲。

## 迭代 5 沉淀：唯一写操作工具的安全设计

F2 批量重命名是整个工具箱**唯一修改磁盘**的工具，也是阶段七定义的阻断级缺陷来源（"静默覆盖原文件"直接阻断发布）。它的安全设计可以作为今后任何写操作工具的模板：

1. **规划与执行彻底分离**：`RenamePlanner.BuildPlan` 是**纯函数**——只根据文件和规则算出"原名 → 新名"列表，绝不碰磁盘。执行集中在唯一的 `RenameExecutor` 类里。这样 90% 的逻辑（规则、非法字符、重名避让）都能脱离文件系统做单元测试，真正写磁盘的代码只有两个 `File.Move`。

2. **防覆盖要做两道校验**：生成计划时避让一次（与磁盘现有文件、计划内新名都比），执行前**再校验一次**（`File.Exists(NewPath)`）——因为从生成计划到用户点确认之间，目标文件可能被别的程序创建。第二道校验是防竞态的关键，绝不能省。`Execute_TargetExists_NeverOverwrites` 这个测试专门守护这条红线：伪造一个指向已存在目标的计划，断言源文件没动、目标内容未被覆盖。

3. **可注入的"已存在文件"让避让可测**：`BuildPlan` 提供一个接收 `existingNames` 集合的重载，单测塞入虚拟的 `{"照片1.jpg", "照片1(1).jpg"}` 就能验证避让到 `(2)`，不用真的在磁盘上建这些文件。这和迭代 4 的"可注入容错"是同一个思路——**把环境依赖变成参数**。大小写不敏感要用 `StringComparer.OrdinalIgnoreCase`（Windows 文件系统语义）。

4. **撤销 = 反转的记录列表**：执行成功的每条都记 `RenameRecord(OldPath, NewPath)` 入栈；`BuildUndoPlan` 纯函数把它逆序反转成"新名 → 原名"的计划。撤销同样走二次校验（原名位置被占用就不恢复，绝不覆盖别人的文件）。界面层用 `lastRecords` 持有记录，执行后启用"撤销上一步"按钮，撤销后清空——保证只能撤销最近一次操作。

## 迭代 6 沉淀：打包发布的三个坑

1. **绝不能用 `PublishSingleFile=true`**：工具靠运行时扫描 `WinTools.Tools.*.dll` 反射发现，单文件发布会把这些 DLL 打进 exe，导致 7 个工具全部消失。发布必须用 `-p:PublishSingleFile=false`，且要把工具 DLL 从 Shell 的 Release 输出目录手动 `cp` 到 `publish/`。详见 `installer/发布说明.md`。
2. **Shell 故意不引用工具项目**：工具 DLL 由 `Directory.Build.props` 的构建后目标复制到 Shell 输出目录，所以 `dotnet publish` 只发布 Shell 本身，不带工具 DLL——这是设计使然，不是 bug。发布步骤里必须显式补拷贝。
3. **Inno Setup 用通配递归收录 publish 整目录**：`Source: "..\publish\*"; Flags: ignoreversion recursesubdirs createallsubdirs; Excludes: "*.pdb"` 一条语句即可覆盖 exe、所有运行时 DLL 与语言子目录（zh-Hans 等），排除 pdb 减小体积。安装包从 108.9 MB 压到约 36 MB。Inno Setup 7.x 的 `ArchitecturesInstallIn64BitMode` 用 `x64compatible`（`x64` 已弃用会告警）。

5. **危险操作的交互规范**：预览表是操作核心（原名/新名/说明三列，逐行可核对）；执行必须弹模态确认框且默认按钮是"取消"；非法字符与重名避让都在"说明"列里明确告知用户；执行后清空源文件列表，避免用户对已改名的文件重复点执行。任何错误都用就地反馈条显示，不弹窗打断——但"二次确认"是唯一例外，因为这是写操作。

## UI 改版沉淀：WinForms 做出原型级界面的五个要点

界面按 `prototype/原型-主界面.html` 重做后（详见 `docs/UI改版说明.md`），新增工具照此办：

1. **样式库放 Core，工具零改宿主也能统一**：`WinTools.Core.Ui` 提供 `UiTheme`/`CardPanel`/`FeedbackBar`/`ToolHeader`。工具类 `using WinTools.Core.Ui;` 即可用，无需改 Shell——这是共享视觉且不破坏插件架构的关键。
2. **字体必须用像素单位**：`new Font("Microsoft YaHei UI", 13F, FontStyle.Regular, GraphicsUnit.Pixel)`，配合主窗 `AutoScaleMode=None`。若用默认 point 单位，高 DPI 屏上字体会被系统放大，而控件是固定像素，导致文字上下重叠（本次第一版就踩了这个坑）。统一用 `UiTheme.Body/Bold/Title/Mono`，别自己 new。
3. **高 DPI 用 .NET 方式配置**：csproj 设 `<ApplicationHighDpiMode>PerMonitorV2</ApplicationHighDpiMode>`，app.manifest 只放 asInvoker 和 longPathAware——若在 manifest 里写 dpiAwareness 会触发 WFO0003 警告。
4. **Dock 添加顺序决定视觉顺序**：FlowLayoutPanel/Panel 里同向 Dock 的控件，**后加的排更靠外（更靠上/下）**。想让视觉从上到下是「A→B→C」，添加顺序要反过来 `C、B、A`；Fill 的控件永远最先加。密码工具第一版把按钮排到了最上、长度排到了最下，就是没注意这条。
5. **验证界面别用屏幕截图**：多 DPI 环境下截屏坐标系错位会产生"文字重影"假象。可靠做法是在 `Shown` 事件里用 `DrawToBitmap` 自绘窗口存 PNG（本次加了环境变量触发的临时钩子，验证后已移除）。

## 迭代 7 沉淀：三个低成本工具一起加

URL 编解码、时间戳转换、环境变量查看三个工具没有新建项目，而是分别塞进现有的 `WinTools.Tools.Text` / `WinTools.Tools.System`。发现器按 DLL 扫描**所有**带 `[Tool]` 的 `ITool` 类型，一个 DLL 放多个工具完全合法，省去改 sln 与发布拷贝清单。

几条新踩/新确认的坑：

1. **本地函数捕获变量要先声明**：`CreateUI` 里先写 `void SetMode(...)` 再用 `var inputBox = ...`，如果函数体读 `inputBox` 会报 CS0841；先声明变量、再写函数。同理，卡片头 `AddAction` 的 lambda 捕获的集合变量也必须在 `AddAction` 之前赋值，否则 CS0165。
2. **`FluentInput` 没有 `Clear()`**：它是复合 `Panel`，对外只有 `new string Text`；清空要写 `inputBox.Text = string.Empty`，别照抄 `TextBox.Clear()`。
3. **时间类逻辑把时区做成参数**：`TimestampConverter.FromTimestamp/FromDateTime` 都接受可选 `TimeZoneInfo`，单测注入 `Utc` 或固定 `+08:00`，断言不受测试机本地时区影响。
4. **URL 解码别只调 `Uri.UnescapeDataString`**：它对非法 `%` 序列静默留原文。自己按字节扫描（`%XX` → byte，`+` → 空格），再用严格 UTF-8 解码，才能把坏输入变成友好提示，且中文/emoji 往返不失真。
5. **只读系统信息也可以可注入**：环境变量用 `CollectFrom(IDictionary)` 与真实 `Collect()` 分开，单测喂伪造字典即可覆盖排序、跳过空键、null 值、筛选与复制格式。
6. **加一条 CreateUI 冒烟测试很值**：发现机制测试除了验证 Id/Name，再对每个新工具调一次 `CreateUI()`，能在不启窗体的情况下抓出布局构造期的空引用/未赋值捕获。

## 迭代 8 沉淀：网络探测与大目录只读扫描

本轮补齐原 20 个候选清单里最后两个可做的工具（N1 Ping 测试、F4 重复文件查找），顺带加了文本统计、UUID 生成。四个都塞进现有三个工具项目，没有新建 csproj、没有改 sln、没有改宿主。

1. **对象初始化器只能跟在 `new` 后面**：`UiTheme.Input(...) { Dock = ... }` 会报一串 CS1002——那是**方法调用**，不是对象创建表达式。要么先声明再逐项赋值，要么直接 `new FluentInput(...)`。本轮 `Input` / `HintLabel` / `Button` 三处都踩了，症状是中文文案那行附近连报十几个"应输入 ;"，容易误判成引号问题。
2. **先用反射确认枚举成员再写 switch**：`IPStatus` 没有 `BadBufferTooSmall` / `PolicyFailure` 这些"看起来应该有"的成员；写之前用 IDE 补全或查枚举定义，别凭印象。状态文案映射做成纯函数 `Describe(IPStatus)` 后，边界可单测，不必真去制造网络故障。
3. **网络/磁盘操作都通过委托注入**：`PingChecker.RunAsync(target, count, probe, token)` 的 `probe` 由界面层传入真实 `Ping.SendPingAsync`，单测塞假 probe 就能覆盖成功、超时、全失败、取消四条路径。`DuplicateFinder.Find(files, hash, minBytes, token)` 同理——哈希函数注入，单测用临时小文件 + 假哈希，不必造大文件。这是迭代 4"可注入容错"思路的推广：**把外部世界变成参数**。
4. **重复文件查找必须两阶段**：先按文件大小分组，大小唯一的文件根本不可能是副本，直接跳过内容读取；只对同大小组算 SHA-256。大目录扫描的耗时几乎全在 I/O，这一步能省掉绝大多数读取。哈希流式读 + `FileShare.ReadWrite`，被其他程序打开的文件也能读；单个文件失败只跳过它，不让整次扫描崩掉。
5. **只读工具的红线写进报告文案**：F4 只输出"哪几份相同、可释放多少"，界面不提供任何删除/移动按钮，报告标题也写明"只报告不删除"——阶段一"不做什么"边界靠代码与文案双重落实。
6. **测试期望值先算一遍再写**：本轮三个失败全是期望写错（emoji 的 UTF-8 是 4 字节、两个汉字是 3+3 而非 2+3、`FormatSize(2048)` 输出 `2.0 KB` 而非 `2 KB`）。实现没问题的时候，先怀疑测试用例的常量。

## 迭代 9 沉淀：截图工具（系统坐标 + 全屏覆盖层）

屏幕截图放进既有 `WinTools.Tools.File`，没新建项目、没改宿主。这类"读屏幕"工具与之前读文件/读系统状态的工具有几个不同的坑：

1. **屏幕坐标是物理像素，绝不能过 `UiTheme.Sx`**：`Screen.VirtualScreen`、`Cursor.Position`、`Graphics.CopyFromScreen` 在 PerMonitorV2 进程里都返回/接受**物理像素**；`UiTheme.S` 只服务于界面控件布局。二者混用会在高缩放屏上截错位置。约定：所有传给抓屏/覆盖层的 `Rectangle` 保持原始物理坐标，只有覆盖层里画提示文字和描边才用 UiTheme 缩放助手。单测用普通 Rectangle 验证逻辑即可，物理语义在 UI 层保证。
2. **覆盖层必须铺满虚拟屏幕而非主屏**：`SystemInformation.VirtualScreen` 可能含负坐标（副屏在主屏左侧），覆盖层 `Location = vs.Location`、`Size = vs.Size`。鼠标拿到的是相对窗体坐标，最后加回 `vs.Location` 才是屏幕坐标。若用 `Screen.PrimaryScreen.Bounds` 会漏掉副屏。
3. **底图只抓一次，框选后从底图裁剪**：先 `CopyFromScreen` 一张全屏底图铺在覆盖层上（选区外盖半透明暗色，选区内重绘亮底图），确认后对同一张底图 `Clone(选区)`。若确认时重新抓屏，光标/界面变化会与所见不一致；而且二次抓屏时覆盖层自己会挡在屏幕上。
4. **抓屏前隐藏宿主窗口**：工具界面本身在屏幕上，不隐藏就会截进画面。用 `FindForm()` 拿到窗口 → `Hide()` → `Application.DoEvents()` → `Thread.Sleep(180)` 等桌面重绘 → 抓屏 → `finally` 里 `Show()` 恢复。隐藏/恢复必须成对放在 try/finally，任何异常路径都不能把用户窗口留在隐藏状态。
5. **抓屏器注入才测得了**：`ScreenCapture.Capture(bounds, Func<Rectangle, Bitmap> grab)` 把真实 GDI+ 抓屏作为参数传入；单测塞假抓屏器即可覆盖成功/抛异常/空图/空区域四条路径，不必依赖测试机有没有显示器。`Crop`、`NormalizeSelection`、`Encode`、`BuildFileName` 都是纯函数，直接测。
6. **剪贴板图片复用文本版兜底**：`ClipboardUtil.TryCopyImage` 沿用 `TryCopy` 的 `ExternalException`/`ThreadStateException` 捕获——远程桌面或剪贴板管理器占用剪贴链时不会让进程崩掉，返回 false 由界面提示降级到「另存为」。
7. **延时浮层用 `System.Windows.Forms.Timer`**：`ImplicitUsings` 同时引入 `System.Threading.Timer`，直接写 `Timer` 会 CS0104 歧义；WinForms 定时器在 UI 线程回调，才能安全更新浮层文字。浮层 Esc 取消走 `DialogResult.Cancel`。
8. **小选区视为误点**：松开鼠标时选区宽或高 < 8px 不直接结束，而是重置为未框选让用户重拖，避免点一下就截出一条线。

## 迭代 10 沉淀：标注编辑与可调整选区

1. **编辑层要拿全屏底图，不要拿裁好的图**：若确认框选后先裁剪再进编辑，用户就无法再移动/调整选区。正确做法是传「整张底图 + 屏幕选区」，编辑器把选区换算成图像坐标（`selection - virtualScreen.Location`），只在输出时才 `Clone(选区)`。底图所有权一并转移给编辑器，调用方别再 Dispose，否则会双重释放。
2. **选区调整做成纯几何函数**：`SelectionGeometry` 提供八向手柄的命中测试、整体移动、按手柄缩放、最小边长与 bounds 钳制，UI 只做坐标换算和光标切换。手柄命中要「四角优先于四边」，否则角点会被相邻的边抢走；命中容差用 `UiTheme.Sx(10)` 跟随 DPI 缩放。
3. **标注固定在内容上，不跟着选区跑**：Stroke 存图像坐标，调整选区只改裁剪框。这样拖动选区时标注不会在画面里漂移，和微信截图一致。每次重绘仍从原始底图叠加命令栈，马赛克才能正确撤销。
4. **预览和裁剪必须同框**：拖拽预览绘制时用 `Graphics.Clip = new Region(选区)` 限制可见范围；否则屏幕上看到选区外有标注，保存出来却没有，用户会以为丢了内容。
5. **工具栏两行比单行滚动好用**：工具行（选择/绘制/颜色/粗细）+ 操作行（撤销/重做/复制/保存/置顶/完成/退出各 68–72px），窄屏也不会把「完成」挤到滚动区外；底部状态标签用于反馈「已复制/已保存」，是低成本的交互反馈。
6. **离屏渲染探针的两种坑**：`DrawToBitmap` 不会画出 Dock 的子控件（只能看到自绘背景）；`CopyFromScreen` 会把前台窗口拍进来。要验证全屏覆盖层布局，用 `Application.Run(form)` + `PrintWindow(form.Handle, hdc, 0)` 抓窗体本身，再裁剪放大看按钮是否重叠。

## 迭代 11 沉淀：单条图标工具栏与二级选项面板

1. **工具栏要一条，不要两行**：参考微信截图，底部一条纯图标栏；颜色/粗细/块大小这类参数点击工具后在按钮下方浮出二级面板，不常驻工具栏。选中工具用绿色填充 + 白色图标，带选项的按钮右下角画小三角。
2. **自绘控件的 WFO1000**：自定义 `Control` 子类的属性（哪怕 `internal`）会触发「没有为属性内容配置代码序列化」错误。给属性加 `[DesignerSerializationVisibility(DesignerSerializationVisibility.Hidden)]` 即可，不必改成字段。
3. **`AutoSize` 不能配 `Dock=Fill` 子容器**：弹出面板最初只有 12×12——内部 FlowLayoutPanel 的 Dock.Fill 把尺寸压没了。改成子容器 `AutoSize=true` + `Location = Padding 左上`，面板 AutoSize 才能包住内容；表情网格需要换行，用固定尺寸并关掉 AutoSize。
4. **面板是独立顶层窗口**：`PrintWindow(主窗体)` 抓不到浮出的面板，要单独对面板句柄再抓一次；`ShowUnder` 先 `Show()` 拿 AutoSize 后的真实尺寸再按工作区钳位，靠近底边时翻到按钮上方。
5. **一键打码是普通命令**：对整个选区压一条 `AnnotationTool.Mosaic` stroke 即可，复用现有渲染与命令栈，天然可撤销，不需要新算法。
6. **状态反馈不占工具条**：「已复制/已保存/块大小 N」做成画布内短暂 toast（Timer 300ms 轮询到期重绘），工具栏就能保持单条。`Timer` 在 ImplicitUsings 下有 WinForms/Threading 歧义，要写全限定名。

## 迭代 12 沉淀：编辑窗口改为图片大小（仿微信截图）

1. **编辑阶段不要铺满整屏**：用户要的是参考图那种「一张图 + 一条工具栏」的独立窗口，不是全屏底图加遮罩。构造函数只收一张已裁好的图，窗口 `ClientSize` 由图片尺寸 + 工具栏高度 + 边距算出来，`Location` 居中于 `Screen.FromPoint(Cursor.Position).WorkingArea`。工具栏 `Location` 紧贴图片下边缘，不 Dock 到屏幕底部。
2. **裁剪在进编辑前完成**：`ScreenshotTool.ShowResult` 把屏幕坐标选区减去 `VirtualScreen.Location` 换算成图像坐标，`Clone(选区)` 后把所有权交给编辑窗口；全屏/延时截图的选区就是整个 vs，不需裁剪。负坐标副屏靠这个减法才不会错位。
3. **大图缩放显示，命令仍用原图坐标**：`scale = min(1, availW/w, availH/h)`，图片按 `_imageRect` 缩放绘制；鼠标点先 `ToImage()` 反算回原图像素再存 Stroke。拖拽预览用 `Graphics.TranslateTransform + ScaleTransform` 在图像坐标系绘制；`TextRenderer` 不跟随 transform，但文字/表情没有拖拽预览，不受影响。
4. **独立窗口要自己画边框和尺寸标签**：无边框窗体用 `DrawRectangle(Accent, _imageRect)` 画绿框，`TextRenderer` 在图片上方画 `宽 x 高`；窗口背景深灰，工具栏白底黑图标（与参考图一致）。
5. **去掉编辑阶段的选区调整**：前移到框选阶段后，`SelectionGeometry` 仍保留为纯逻辑与单测资产，但编辑层不再引用；工具栏不再有「选择」按钮，默认工具是矩形。
6. **验证方式**：用一次性探针 `new AnnotationOverlay(fakeBitmap)` + `form.Show()` + `PrintWindow` 抓窗体，打印 `form.Size` 确认是图片尺寸而非整屏；二级面板是独立顶层窗口，要单独抓。反射 `GetField("_toolButtons")` 取按钮后，`Control.OnClick` 的非公开反射调用可触发自绘按钮的 Click。

## 迭代 13 沉淀：全局快捷键、托盘与自动复制

宿主除 `ITool` 外还认两个**可选**接口，工具需要才实现，不实现行为完全不变：

| 接口 | 调用时机 | 用途 |
|---|---|---|
| `IBackgroundTool` | 宿主 `OnLoad` 调 `Start`，真正退出时调 `Stop` | 全局热键、文件监听等"窗口没开也要工作"的能力 |
| `IToolCommand` | 托盘菜单等外部入口按命令 id 调 `TryInvoke` | 外部触发工具能力（如 `capture-region`），宿主不认具体工具 |

几条关键约束：

1. **后台状态不能挂在页面控件上**：`CreateUI` 的结果会被宿主缓存、也会因切主题重建，页面控件随时可能被 Dispose。热键、监听器这类进程级状态放进工具 DLL 的静态类（见 `ScreenCaptureRuntime`），页面只读写它，并在 `VisibleChanged` 时回填，避免重新打开看到旧值。
2. **全局热键用消息专用窗口**：`HotkeyWindow` 以 `HWND_MESSAGE` 建窗后 `RegisterHotKey`，必须创建在有消息循环的 UI 线程。窗口隐藏、宿主最小化都不影响热键；进程退出即释放。注册失败最常见的原因是组合已被其它程序占用（错误码 1409），要给用户可读原因而不是一个数字。
3. **录入热键前必须注销**：按下当前生效的组合时，`WM_HOTKEY` 会先把功能拉起来，录入框根本收不到按键。把 `Suspend()/Resume()` 挂在输入框的 `GotFocus/LostFocus` 上。
4. **关窗 ≠ 退出**：一旦提供全局热键，主窗口就必须"关闭即收进托盘"，否则进程退出后热键失效。`FormClosing` 里只在 `CloseReason.UserClosing` 时取消关闭；`TaskManagerClosing`（外部投递 WM_CLOSE、任务管理器结束）仍应真正退出。
5. **剪贴板图片要保活**：`Clipboard.SetImage` 只存位图引用，立刻 Dispose 会让粘贴出来是空白。热键路径把结果图留在运行时静态字段，下一次截图再替换。
6. **反馈不能依赖主窗口**：窗口隐藏时没有界面可写，用 `WS_EX_NOACTIVATE + WS_EX_TOOLWINDOW` 的浮条（`CaptureToast`）提示结果，不抢焦点、自动消失。
7. **验证注入按键不可靠**：`keybd_event`/`SendInput` 在部分机器上会被安全软件或 UIPI 丢弃（对照普通窗体同样收不到）。可自动化验证的是「`RegisterHotKey` 返回成功」+「投递 `WM_HOTKEY` 能按 id 分发到回调」+「Runtime 触发的完整截图链路」，真实按键留给人工确认。

## 迭代 14 沉淀：滚动截图

滚动截图 = 「固定区域反复抓屏 + 按重叠内容拼接」。屏幕本身没有滚动事件可听，只能靠画面推断滚了多少：

| 部分 | 职责 |
|---|---|
| `ScrollStitcher` | 纯逻辑：逐行采样哈希定位重叠行数，只追加新露出的行；可拿合成图片单测 |
| `ScrollCaptureForm` | 采集浮条：定时抓屏、显示进度、完成/取消，贴在选区外侧 |
| `ScreenshotRunner` | 把「框选 → 采集 → 标注」串成与其它模式一致的一条流程 |

几条关键约束：

1. **比较 `上一帧底部` 与 `新帧顶部`，追加起点是 `topSkip + overlap`**：重叠部分要丢掉，只追加 `frameHeight - topSkip - overlap` 行。这里漏加 `overlap` 会把已拼过的内容再拼一遍（表现为长图在接缝处重复一段），单测的逐像素比对就是用来抓这个的。
2. **纯色行必须剔除**：空白页/大段留白里任意两段都能"完美匹配"，不剔除会得到随机位移。用每行采样点的明暗极差判断"是否有信息"，信息行不足 8 行时宁可判失败。
3. **固定头部要单独处理**：网页常有吸顶导航，每帧都在顶部。检测"两帧开头连续相同的行数"，把它作为 `topSkip` 跳过匹配；这样成品里头部只出现一次，也不会把头部重复拼进正文。
4. **找不到重叠时不要硬拼**：滚太快（位移超过一屏）、区域里有视频/动画、或者用户滚回去了，都会对不上。此时报"这一帧对不上"并保留已有内容，比悄悄拼错强。
5. **浮条不能出现在截图里**：优先放到选区外（下 → 上）；选区占满屏幕时只能压在选区上，抓屏瞬间把 `Opacity` 归零，抓完立刻恢复。只隐藏 20~30ms，肉眼几乎看不出闪烁。
6. **`WS_EX_NOACTIVATE` 不等于绝对不抢焦点**：本机实测（对照最小窗体同样复现）显示顶层无激活窗口仍可能成为前台窗口，导致键盘滚动失效。做法是在 `OnHandleCreated` 记住原前台窗口，`OnShown` 里发现被抢就用 `SetForegroundWindow` 还回去。滚轮本身发给光标下的窗口，不受影响。
7. **超长图必须给标注窗加平移**：一张 1000×6000 的图按整屏适配后宽度只剩一百多像素，根本没法画。判定"按整张适配后宽度 < 380"时改为按宽度适配 + 滚轮上下平移，坐标换算里要加 `_viewTop`，绘制预览命令时先 `SetClip` 再变换，否则笔迹会画到工具栏上。
8. **采集频率 300ms**：比人正常滚动的节奏快，能保证每次滚动至少抓到一帧；页面惯性滚动时也不会漏太多。高度上限 16000px，约 1000 宽时 64MB，可防止长列表把内存吃满。

## 迭代 15 沉淀：从编辑窗再发起一次采集

滚动截图原来只有「先选模式再框选」一个入口，用户截完一块才发现是长页面，只能退出重来。现在标注工具栏上多了一个「滚动截图」按钮，点它即可按当前区域重新采集。做法上有几点值得复用：

1. **编辑窗不直接调用截图流程**：`AnnotationOverlay` 只暴露 `ScreenRegion` + `ScrollCapture` 回调，真正抓屏由 `ScreenshotRunner` 注入。这样编辑窗不知道 `ScrollStitcher` / `ScrollCaptureForm` 的存在，单测和探针也能塞一个假回调进来看按钮行为。
2. **用 `DialogResult.Retry` 表示"换图重来"**：回调成功就存下长图、以 Retry 关闭本次编辑，宿主在循环里带着新图重开编辑；不要试图在原窗体里替换图片重新排版——窗口尺寸、工具栏、命令栈全都要重建，成本远高于重开。
3. **采集前必须 `Hide()` + 等重绘**：编辑器盖在选区上，不藏起来就会把工具栏拍进首帧；`Hide()` 之后那块区域还是旧像素，要 `Application.DoEvents()` 再 `Thread.Sleep(80)`，让桌面把底层窗口重绘出来。探针对首帧与原内容做逐像素比对（平均差 < 3）才敢说没残影。
4. **取消要能回到原状态**：回调返回空时不改 `DialogResult`，只 `Show()` + 提示，用户的标注栈原样保留。这条比"成功路径"更容易被忽略，探针里专门有一条用例。
5. **工具栏宽度要按内容算，不要靠眼睛**：加一个按钮就可能把最后一列挤出白条。`minBarW` 从 520 放到 600，并在交互探针里断言"所有按钮宽度之和 ≤ 工具栏可用宽度"，以后再加按钮会直接报错而不是悄悄裁掉。

## 迭代 16 沉淀：截图自动识别桌面窗口

需求是"截图时能自动认出微信、浏览器、任务栏这些界面，省去人工框选"。屏幕本身没有窗口概念，只能向系统要，于是拆成三层：

| 部分 | 职责 |
|---|---|
| `WindowEnumerator`（Core） | `EnumWindows` 枚举顶层窗口 + 过滤 + 排序，返回物理像素矩形 |
| `WindowClassifier`（Core） | 进程名 → 中文应用名与类别（微信 / Chrome 浏览器 / 任务栏…），纯函数 |
| `SelectionOverlay`（Tools） | 把候选窗口画成带编号的框，接收数字键 / Tab / 悬停 / 点击 |

几条踩过的坑：

1. **任务栏带 `WS_EX_TOOLWINDOW`，按工具窗口一刀切会把"电脑底部的工具栏"滤掉**。规则要写成"工具窗口且不是任务栏才排除"。这条有单测守着，否则改一次过滤规则就可能悄悄把任务栏弄丢。
2. **别用 DWM 的 `DWMWA_EXTENDED_FRAME_BOUNDS`**。它理论上更贴合内容、不含阴影，但实测在远程/虚拟桌面环境下会返回完全对不上的坐标（620×480 的窗口报成 1186×620 且位置漂到屏幕另一角），候选框会框到空气。`GetWindowRect` 稳定，而且它给出的正是"窗口在屏幕上的矩形"，与用户理解的"界面区域"一致。最大化窗口多出的几像素不可见边框，交给"与屏幕求交集"处理。
3. **坐标系必须与抓屏一致**。窗口坐标来自 `GetWindowRect`，抓屏坐标来自 `Graphics.CopyFromScreen`，两者必须都在物理像素系里。进程若被系统做 DPI 虚拟化，窗口坐标会缩一半而抓屏坐标不变，选框整体错位。所以进程必须声明 PerMonitorV2 —— 用 `ApplicationConfiguration.Initialize()`（`ApplicationHighDpiMode=PerMonitorV2`），**不要**往自定义 manifest 里塞 `dpiAware`，分析器会报 WFO0003。
   写验证探针时也要注意：探针工程若没声明 DPI 感知，测出来的永远是错的坐标，排查时容易误判成产品 bug。
4. **矩形完全相同的窗口只保留最上面那个**。全屏应用（浏览器、IDE）常常彼此完全重叠，全都列出来会让编号牌叠成一坨、只看得见一个。合并后候选更清爽。
5. **编号牌要会自动错开**。两个窗口位置完全一致时，把编号牌沿右方向挪，避免叠在一起看不见。
6. **激活标签放在候选框内侧右下角，不要放框外上方**。候选框经常就是从屏幕 (0,0) 开始的整屏窗口，放框外上方会盖住左上角的提示条。
7. **点击候选与手动框选要能共存**：按下与抬起位移 ≤6px 且落点在某个候选内才算"点选"，否则按原来的拖动框选处理。用户点一下想选窗口，拖一下想画框，两种意图不能打架。
8. **常驻列表会挤掉别的卡片**。工具页的纵向空间由 `FluentScrollPanel` 承担，但 `Dock=Fill` 的卡片在溢出时是被压扁而不是撑出滚动区。所以窗口列表做成按需弹出的浮层（`WindowPickerForm`），而不是常驻表格卡片。
9. **浮层的 Dock 顺序**：WinForms 按 z 序从高到低分配空间，后加的先占。顺序必须是 `Fill(列表) → Bottom(提示) → Top(标题栏)`，否则标题栏被列表盖住，或列表第一行被标题栏压住。
10. **窗口范围截图仍然是"所见即所得"**：被别的窗口挡住的部分截不到。这与微信、Snipaste 等主流工具一致（想拿被遮挡内容得用 PrintWindow，而现代 GPU 应用的窗口用 PrintWindow 常常返回黑屏）。

## 迭代 17 沉淀：选区高亮与可调整

原来「松手即确认」，选区一旦抬键就消失，没法微调。现在把一次截图交互拆成三段：

| 阶段 | 进入方式 | 可做的事 |
|---|---|---|
| 框选 / 识别 | 拖动拉框；点编号；数字键 1~9 | 悬停候选整块提亮 |
| 调整 | 松手或点选后 | 八个手柄改四边、框内拖动整体平移、框外重画 |
| 落定 | 双击框内 / `Enter` | 把选区交回截图流程 |

几条实现要点：

1. **每次按下都必须记录选区快照**。手柄拖动和整体移动都从「按下瞬间的矩形 + 鼠标位移」算出新矩形。实际开发中漏掉手柄分支的快照，结果拿 `Rectangle.Empty` 去算边界，拖一次就把选区压没了——这种 bug 肉眼看着像"手柄没生效"，单靠截图很难定位，所以探针里要断言拖动后的精确矩形。
2. **手柄命中优先级：四角 → 四边 → 框内移动**。四角同时属于两条边，先判角再判边；命中范围比手柄可见尺寸略大（`UiTheme.Sx(9)`）才好用。光标要跟着命中结果切换成 `SizeWE` / `SizeNS` / `SizeNWSE` / `SizeNESW` / `SizeAll`，用户不用试就知道该怎么拖。
3. **边界调整只动一边，对边保持不动**，并用 `Rectangle.FromLTRB` 重建；最小边长 16 物理像素，四边都夹在客户区内。整体平移只改位置不改尺寸，同样夹在屏内。
4. **坐标系别混**：选区、手柄位置、命中判定全用客户区物理像素（= 屏幕物理像素减虚拟屏原点），只有手柄的可见尺寸、边框粗细和文字用 `UiTheme` 的缩放助手。PerMonitorV2 下两者混用会在 125%/150% 屏上错位。
5. **候选高亮的画法**：暗色遮罩铺完之后，把 `_backdrop` 的对应矩形用 `DrawImage` 盖回去，就是"整块提亮"；再画实线边框和标签。绘制顺序是「候选高亮 → 选区 → 提示条」，选区定下来后候选降为淡虚线，避免两套边框打架。
6. **预设选区也要走同一个覆盖层**。「桌面窗口」列表点出的矩形原本直接截图，跳过选框层，用户就没法调边界。改成把矩形预填成"已定选区"状态（`initialSelection` 参数），所有入口共用一条路径，行为不分叉。
7. **通用提示由覆盖层统一补齐**。滚动截图等入口传进来的自定义文案只描述本模式的目的；"拖边 / 移动 / 确认 / 取消"由覆盖层统一追加，否则新增入口很容易漏写确认方式，用户对着旧文案「松开后自动拼接」却等不到拼接。
8. **探针要跟着交互一起改**：所有模拟框选的地方（截图交互、窗口识别、热键端到端、滚动）在 `OnMouseUp` 后都要补一次 `OnKeyDown(Enter)`。漏掉的那个探针会一直等标注窗出现，表现为进程卡住而不是普通的断言失败。

## 迭代 18 沉淀：单击确认、无黑边、窗口边界精度

三条来自实际使用的反馈，各自对应一类容易忽略的问题：

1. **"按 Enter 确认"是把内部状态暴露给了用户**。选区调整阶段的 `Enter` 是技术上最简单的落定方式，但用户只想点一下。改法是在 `OnMouseUp` 里区分「按下与抬起几乎同点」（≤6px）与「拖动过」：前者确认，后者仍停留在调整状态。手柄拖动走的是另一条分支，不会被误判；`Enter` 和双击保留作备选。**提示条文案必须同步改**，否则用户仍按旧说明去找 Enter。
2. **编辑器图片周围的深色画布不是"背景"，是没算进去的留白**。原布局把图片放在 `(pad, labelH)`，窗体宽度取 `max(图片宽, 工具栏最小宽) + pad*2`，于是大图四周多出十几像素黑边、顶部还有一行尺寸文字。改成图片从 `(0,0)` 开始、窗宽等于图片宽（工具栏宽度兜底）、尺寸文字移除。底部工具栏是操作入口，保留。**改动前先确认探针没有断言那些装饰值**，否则一改就红。
3. **窗口边界要的是"可见边框"，不是"窗口矩形"**。`GetWindowRect` 会把 DWM 投下的不可见阴影算进去（本机实测每边多 11px），所以识别框比窗口实际内容大一圈。DWM 的 `DWMWA_EXTENDED_FRAME_BOUNDS` 正是排除阴影后的边界，但它在远程/虚拟桌面可能返回离谱坐标。稳妥做法是两者取交：**DWM 结果必须不比 `GetWindowRect` 大、四边贴合、每边收缩 ≤32px，否则回退**。这个"可信性"判断抽成纯函数单独单测——真机上 DWM 抽风很难复现，靠集成测试守不住。
4. **探针的"暗态"基准要自己造**。验证悬停高亮时，真实鼠标可能恰好停在候选上，导致"悬停前"截图已经是亮的。先把 `_hoverIndex` 强制设为 -1 取基准，再设为目标索引取亮态，才能稳定比对像素。
