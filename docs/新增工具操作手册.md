# 新增工具标准操作手册

> 用途：后续 6 个工具（T1/T2/T4/F1/S1/S2/F2）都照这份手册做，不用重新设计。
> 来源：阶段六迭代 1 要求把趟平的过程沉淀成模板；迭代 0 先给出可执行的骨架。
> 前置：已理解阶段三的 `ITool` 接口与发现机制。

---

## 核心原则

宿主（WinTools.Shell）**永远不用改**。新增工具全过程只跟新项目打交道，Shell 源码一行不动。如果你发现自己正在改 MainForm.cs 或 ToolDiscovery.cs 来"接入"新工具——停下来，方向错了。

架构之所以能做到这一点：Shell 运行时扫描 `WinTools.Tools.*.dll`，靠 `[Tool]` 特性 + 反射自动发现。`Directory.Build.props` 负责把工具 DLL 复制到 Shell 输出目录。

## 标准五步

### 第 1 步：建项目

在 `src/` 下新建类库项目，命名**必须以 `WinTools.Tools.` 开头**（发现器靠这个前缀识别）：

```bash
# 以文本工具为例，同一项目可放多个工具类
dotnet new classlib -n WinTools.Tools.Text -o src/WinTools.Tools.Text -f net10.0-windows
```

把生成的 `Class1.cs` 删掉。编辑 csproj 确认内容如下（关键是 `UseWindowsForms` 和 Core 引用）：

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0-windows</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <UseWindowsForms>true</UseWindowsForms>
  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="..\WinTools.Core\WinTools.Core.csproj" />
  </ItemGroup>
</Project>
```

把项目加入解决方案：

```bash
dotnet sln WinTools.sln add src/WinTools.Tools.Text/WinTools.Tools.Text.csproj
```

> 不需要手动配置 DLL 复制——`Directory.Build.props` 会自动把所有 `WinTools.Tools.*` 项目的产物复制到 Shell 目录。

### 第 2 步：实现 ITool（元数据 + 界面）

新建工具类，照抄 `HelloTool.cs` 的结构：

```csharp
using System.Windows.Forms;
using WinTools.Core;

namespace WinTools.Tools.Text;

[Tool(Order = 10)]   // Order 越小，导航越靠前
public sealed class JsonFormatterTool : ITool
{
    public string Id => "json-formatter";        // 全局唯一，小写英文+连字符
    public string Name => "JSON 格式化";
    public string Category => "文本工具";          // 同类工具用相同分类，会自动分组
    public System.Drawing.Icon? Icon => null;

    public Control CreateUI()
    {
        // 在这里构建并返回这个工具的主界面（WinForms 控件）。
        // 遵循阶段四规范：输入区 + 操作按钮 + 结果区 + 错误提示。
        var panel = new Panel { Dock = DockStyle.Fill };
        // ... 具体控件
        return panel;
    }
}
```

**元数据约定**（保持导航整洁）：
- `Id`：全局唯一，用"类名小写+连字符"，一经发布不要改（设置按 Id 存储）。
- `Category`：目前用「文本工具 / 文件工具 / 系统工具 / 其他」四类，与阶段四原型一致。
- `Order`：同类里按使用频率排，主推工具给小数值（如 10、20）。

### 第 3 步：写核心逻辑（放独立类，便于单测）

**关键**：不要把业务逻辑写进 `CreateUI` 的事件处理器里。把它抽成纯逻辑类，这样单元测试能直接测它——这是阶段七测试策略的前提。

```csharp
// JsonFormatter.cs —— 纯逻辑，无 UI 依赖
public static class JsonFormatter
{
    public static string Format(string input) { /* ... */ }
}
```

界面代码只负责：收集输入 → 调用逻辑类 → 显示结果 → 捕获异常显示错误提示。

### 第 4 步：写单元测试

在 `tests/WinTools.Tools.Tests/` 建对应测试类，覆盖正常输入 + 异常路径。用例来自阶段二该工具的 AC 用例 + 阶段七的单元测试清单。

```csharp
[Fact]
public void Format_InvalidJson_ReturnsFriendlyError()
{
    var result = JsonFormatter.Format("{ bad }");
    Assert.False(result.Success);
    Assert.Equal(string.Empty, result.Text); // 不输出半成品
}
```

> 完整范例见 `tests/WinTools.Tools.Tests/JsonFormatterTests.cs`（T1-AC1~AC4 全覆盖，可直接照抄结构）。

### 第 5 步：编译并验证自动发现

```bash
dotnet build WinTools.sln
```

验证清单（照阶段三"空工具验证四步骤"）：
- [ ] 编译成功，工具 DLL 出现在 Shell 的 `bin\Debug\net10.0-windows\` 目录。
- [ ] 启动 Shell，左侧导航出现新工具的「分类 → 名称」。
- [ ] 点击导航项，内容区显示工具界面。
- [ ] **反证**：删除该 DLL 后重启，导航项消失，而 Shell 源码一行未改。

## 常见坑位

| 现象 | 原因 | 解决 |
|------|------|------|
| 导航里没有新工具 | 项目名没以 `WinTools.Tools.` 开头 | 按约定重命名项目 |
| DLL 没复制到 Shell 目录 | `Directory.Build.props` 未生效 / 项目名不符 | 检查文件名与项目名；重新生成解决方案 |
| 编译报"找不到 ITool" | 忘了引用 Core 项目 | csproj 加 `ProjectReference` |
| 编译报"找不到 Control/Icon" | 忘了 `UseWindowsForms=true` | csproj 加上 |
| 工具点击就崩溃 | `CreateUI` 抛异常 | 检查构造逻辑；Shell 已有兜底会显示错误区，但应修根因 |
| 改了代码但界面没变 | 旧 DLL 还在 Shell 目录 | 清理后重新生成（`dotnet clean` 再 `build`） |
| 中文被转义成 `\u4E2D` | `System.Text.Json` 默认转义非 ASCII | 序列化选项加 `Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping`（T1-AC4） |
| 测试 DLL 被当成工具复制 | 测试项目名以 `WinTools.Tools.` 开头 | 保持测试项目名不带该前缀；发现器与复制规则已双重排除 `.Tests` |
| 新增工具发现不到（有多个工具时） | 独立加载上下文里 Core 被重复加载，类型不兼容 | `ToolDiscovery` 的 `Resolving` 回调复用默认上下文的已加载程序集（迭代 1 已修） |
| 编译报 CS0009/CS2012"文件被占用" | 杀毒软件实时扫描新 DLL（本机实测是 **360rp.exe**）/ 测试宿主残留句柄 | 报错信息会点名锁定进程（如"文件被 360rp.exe 锁定"）；最有效解法是**删掉该项目被锁的 `bin`/`obj` 目录后一次性重编译**，缩短杀软介入窗口：`rm -rf tests/<项目>/bin tests/<项目>/obj` 再 `dotnet test`；或 `dotnet build-server shutdown` 后关掉正在运行的 Shell.exe 再编译 |
| `File.WriteAllBytes` 报"命名空间中不存在该类型" | 新建的工具项目命名空间叫 `WinTools.Tools.File`，与 `System.IO.File` 类冲突——同在 `WinTools.Tools.*` 下时，`File` 优先解析成那个子命名空间 | **命名空间用复数 `WinTools.Tools.Files`，但项目名/程序集名保持 `WinTools.Tools.File`**（复制规则靠项目名前缀，发现靠 `[Tool]` 特性，都不依赖命名空间）。迭代 3 踩过 |
| xUnit 报"could not find dependent assembly"/"没有可用测试" | 360 锁定导致测试依赖没复制全 | 删掉测试项目 `bin`/`obj` 重新 `dotnet test`；不要盲目加 `--no-build` |
| 哈希测试断言大小写不符 | `Convert.ToHexString` 输出**大写**（与 certutil 一致），标准向量常写成小写 | 期望值统一 `.ToUpperInvariant()` 再比较；逻辑保持大写不改 |
| 项目名带 `.System` 导致命名空间冲突 | 命名空间若叫 `WinTools.Tools.System` 会和 BCL 的 `System` 根命名空间混淆 | 命名空间用 `WinTools.Tools.SystemTools`，项目名保持 `WinTools.Tools.System`（复制规则靠项目名） |
| 编译报 CS1002"应输入 ;"（中文文案那行） | 字符串内容里混进了 **ASCII 直引号**，提前终止了字符串 | 文案里的引号用中文书名号 `「」` 或全角引号；代码定界符才用 ASCII 直引号 |
| 编译报 CS0663"仅 out/ref 不同不能重载" | P/Invoke 方法 `GlobalMemoryStatusEx(ref X)` 与包装方法 `GlobalMemoryStatusEx(out X)` 同名 | 包装方法换个名字（如 `TryGetMemoryStatus`） |
| 编译报 CS0118"'Cursor' 是类型但用作变量" | 在 ITool 实现类的局部函数里写 `Cursor = ...`，被解析成 `System.Windows.Forms.Cursor` 类型 | 用具体控件 `.Cursor`，或直接不用等待光标 + `Application.DoEvents()` |


## 迭代 3 沉淀：文件类 + 异步工具的标准做法

F1 哈希是第一个"读写文件 + 异步"工具，以下做法可直接复用到迭代 4、5：

1. **一次读取，多路消费**：同时算 MD5/SHA1/SHA256 时，别读三遍文件。用三个 `IncrementalHash`，每次读到一块 `span` 就依次 `AppendData` 给三个实例——只读一遍磁盘，内存恒定。迭代 5 的文件操作也应避免整文件载入内存。

2. **异步 ≠ 在 UI 线程外碰控件**：`FileHasher.ComputeAsync` 是纯逻辑，不碰任何控件；进度通过 `IProgress<int>` 回传。`new Progress<int>(...)` 的回调**自动在 UI 线程执行**，可以安全地更新进度条/标签——这是 WinForms 异步的安全通道，不要图省事在后台线程直接改控件。

3. **被占用文件要能读**：`FileStream` 用 `FileShare.ReadWrite`（而非默认 `Read`），否则用户用 Word/记事本打开着的文件会读取失败。配合"每个文件 try-catch 转成结果对象"，做到一个失败不影响其他（F1-AC4）。

4. **大文件用 `ArrayPool<byte>`**：1MB 缓冲区若每次 `new` 会造成 GC 压力；用 `ArrayPool.Shared.Rent/Return` 复用。配合 `FileOptions.Asynchronous | SequentialScan` 提示系统优化顺序读。

5. **标准向量测试不要依赖外部命令**：`certutil` 在不同 Windows 版本输出格式/大小写可能不同，测试应自包含——硬编码公认向量（注意大写），或对大文件用 .NET 内置 `MD5.HashData` 等一次性 API 交叉验证。

## 迭代 4 沉淀：系统类工具的两个可测试设计

S1、S2 都是"读系统状态"的工具，这类工具的共性难题是**环境不可控、难以在测试里复现**。两个设计值得复用：

1. **可注入的容错（S1）**：把每个字段的读取做成 `Func<string>` 委托，通过 `CollectFrom(sources)` 注入。生产用 `Collect()` 传真实读取器；测试传入一个"会抛异常的委托"，就能稳定验证"该项标记不可用、其余正常"——不必真的去破坏系统配置。这是让"容错"这件事可自动化验证的关键，呼应阶段七 S1 单测要求。

2. **纯函数解析 + 薄封装（S2）**：端口查询依赖 `netstat` 这个外部命令，但它把"启动进程取输出"（`GetListeningPids`）和"解析文本"（`ParseListeners(string)`）拆开了。解析是纯函数，单测只要喂一段样例文本（英文格式、IPv6、中文 Windows 格式各一份），就能验证正确性，完全不依赖测试机上哪些端口正被占用。实际 netstat 输出格式已在本机核对（列顺序 fixed，LISTENING 关键字中英文一致）。

3. **零第三方依赖读系统信息**：CPU 从注册表 `HKLM\HARDWARE\DESCRIPTION\System\CentralProcessor\0` 读 `ProcessorNameString`；内存用 P/Invoke `GlobalMemoryStatusEx`；磁盘用 `DriveInfo`。全部只读、普通权限、无需 WMI 或 NuGet 包——符合阶段五"供应链最小化"。注意 `ulong` 字节数转 `long` 要显式转换，P/Invoke 包装方法别和原生方法同名（否则 out/ref 重载冲突）。

## 迭代 2 沉淀：一次流程验证，两个新经验

迭代 2 同时加了两个工具（T2 Base64、T4 密码），全程照抄迭代 1 建立的模板，没有再踩新的架构坑——这证明模板是可靠的。补充两条值得记住的经验：

1. **密码生成必须用密码学安全随机数**：`RandomNumberGenerator.GetInt32(n)` 而非 `Random`。`Random` 是可预测的（种子可推导），生成的密码不安全。这里用了一个源码审查测试（`Generate_SourceUsesCryptoRng_NotRandom`）来守护这条安全底线——它读取自己的源码，确认没有 `new Random(`。测试项目用 csproj 的 `Content` 项把源文件复制到输出目录，用 `AppContext.BaseDirectory` 定位，避免相对路径不稳定。
2. **"满足所有勾选条件"需要主动保证**：如果只从合并字符集里纯随机取字符，可能某种类型一个都没抽到（例如勾了数字但 16 位里没有数字）。做法是先从每个勾选的字符集各取一个字符，再补齐剩余，最后用 Fisher-Yates 洗牌打散顺序。这样既满足 AC2，又不失去随机性。

3. **构造测试用例时先核对基准串**：本轮一个测试失败是自己手误——把 Base64 基准串里的 `s` 写成了逗号，导致解码断言失败。教训：写编解码往返测试的常量时，用工具生成的准确值，不要手敲。

## 迭代 5 沉淀：唯一写操作工具的安全设计

F2 批量重命名是整个工具箱**唯一修改磁盘**的工具，也是阶段七定义的阻断级缺陷来源（"静默覆盖原文件"直接阻断发布）。它的安全设计可以作为今后任何写操作工具的模板：

1. **规划与执行彻底分离**：`RenamePlanner.BuildPlan` 是**纯函数**——只根据文件和规则算出"原名 → 新名"列表，绝不碰磁盘。执行集中在唯一的 `RenameExecutor` 类里。这样 90% 的逻辑（规则、非法字符、重名避让）都能脱离文件系统做单元测试，真正写磁盘的代码只有两个 `File.Move`。

2. **防覆盖要做两道校验**：生成计划时避让一次（与磁盘现有文件、计划内新名都比），执行前**再校验一次**（`File.Exists(NewPath)`）——因为从生成计划到用户点确认之间，目标文件可能被别的程序创建。第二道校验是防竞态的关键，绝不能省。`Execute_TargetExists_NeverOverwrites` 这个测试专门守护这条红线：伪造一个指向已存在目标的计划，断言源文件没动、目标内容未被覆盖。

3. **可注入的"已存在文件"让避让可测**：`BuildPlan` 提供一个接收 `existingNames` 集合的重载，单测塞入虚拟的 `{"照片1.jpg", "照片1(1).jpg"}` 就能验证避让到 `(2)`，不用真的在磁盘上建这些文件。这和迭代 4 的"可注入容错"是同一个思路——**把环境依赖变成参数**。大小写不敏感要用 `StringComparer.OrdinalIgnoreCase`（Windows 文件系统语义）。

4. **撤销 = 反转的记录列表**：执行成功的每条都记 `RenameRecord(OldPath, NewPath)` 入栈；`BuildUndoPlan` 纯函数把它逆序反转成"新名 → 原名"的计划。撤销同样走二次校验（原名位置被占用就不恢复，绝不覆盖别人的文件）。界面层用 `lastRecords` 持有记录，执行后启用"撤销上一步"按钮，撤销后清空——保证只能撤销最近一次操作。

## 迭代 6 沉淀：打包发布的三个坑

1. **绝不能用 `PublishSingleFile=true`**：工具靠运行时扫描 `WinTools.Tools.*.dll` 反射发现，单文件发布会把这些 DLL 打进 exe，导致 7 个工具全部消失。发布必须用 `-p:PublishSingleFile=false`，且要把工具 DLL 从 Shell 的 Release 输出目录手动 `cp` 到 `publish/`。详见 `installer/发布说明.md`。
2. **Shell 故意不引用工具项目**：工具 DLL 由 `Directory.Build.props` 的构建后目标复制到 Shell 输出目录，所以 `dotnet publish` 只发布 Shell 本身，不带工具 DLL——这是设计使然，不是 bug。发布步骤里必须显式补拷贝。
3. **Inno Setup 用通配递归收录 publish 整目录**：`Source: "..\publish\*"; Flags: ignoreversion recursesubdirs createallsubdirs; Excludes: "*.pdb"` 一条语句即可覆盖 exe、所有运行时 DLL 与语言子目录（zh-Hans 等），排除 pdb 减小体积。安装包从 108.9 MB 压到约 36 MB。Inno Setup 7.x 的 `ArchitecturesInstallIn64BitMode` 用 `x64compatible`（`x64` 已弃用会告警）。

5. **危险操作的交互规范**：预览表是操作核心（原名/新名/说明三列，逐行可核对）；执行必须弹模态确认框且默认按钮是"取消"；非法字符与重名避让都在"说明"列里明确告知用户；执行后清空源文件列表，避免用户对已改名的文件重复点执行。任何错误都用就地反馈条显示，不弹窗打断——但"二次确认"是唯一例外，因为这是写操作。

## UI 改版沉淀：WinForms 做出原型级界面的五个要点

界面按 `prototype/原型-主界面.html` 重做后（详见 `docs/UI改版说明.md`），新增工具照此办：

1. **样式库放 Core，工具零改宿主也能统一**：`WinTools.Core.Ui` 提供 `UiTheme`/`CardPanel`/`FeedbackBar`/`ToolHeader`。工具类 `using WinTools.Core.Ui;` 即可用，无需改 Shell——这是共享视觉且不破坏插件架构的关键。
2. **字体必须用像素单位**：`new Font("Microsoft YaHei UI", 13F, FontStyle.Regular, GraphicsUnit.Pixel)`，配合主窗 `AutoScaleMode=None`。若用默认 point 单位，高 DPI 屏上字体会被系统放大，而控件是固定像素，导致文字上下重叠（本次第一版就踩了这个坑）。统一用 `UiTheme.Body/Bold/Title/Mono`，别自己 new。
3. **高 DPI 用 .NET 方式配置**：csproj 设 `<ApplicationHighDpiMode>PerMonitorV2</ApplicationHighDpiMode>`，app.manifest 只放 asInvoker 和 longPathAware——若在 manifest 里写 dpiAwareness 会触发 WFO0003 警告。
4. **Dock 添加顺序决定视觉顺序**：FlowLayoutPanel/Panel 里同向 Dock 的控件，**后加的排更靠外（更靠上/下）**。想让视觉从上到下是「A→B→C」，添加顺序要反过来 `C、B、A`；Fill 的控件永远最先加。密码工具第一版把按钮排到了最上、长度排到了最下，就是没注意这条。
5. **验证界面别用屏幕截图**：多 DPI 环境下截屏坐标系错位会产生"文字重影"假象。可靠做法是在 `Shown` 事件里用 `DrawToBitmap` 自绘窗口存 PNG（本次加了环境变量触发的临时钩子，验证后已移除）。

## UI 改版 v2 沉淀（ToolBox 四原型图）

按四张 ToolBox 原型图二次改版后（工具目录首页 / 双主题 / 搜索页 / 两栏工作台），新增经验：

6. **主题色要"属性化"而非"字段化"**：把 `UiTheme.X` 从 `readonly Color` 字段改成按 `CurrentTheme` 取值的属性，切换主题时广播 `ThemeChanged`，宿主重建界面即可全局换肤。若用 readonly 字段，切换主题后已创建的控件颜色不会更新。
7. **Dock.Fill 控件必须在索引 0**：`Panel.Controls` 里 Fill 控件若不是在集合最前（如夹在 Left 与 Right 之间添加），会遮挡 Left 控件——标题栏四点 Logo 一度消失就是 `Dock.Fill` 的 searchHost 挡住了 `Dock.Left` 的 brandArea。修复用 `Controls.SetChildIndex(fillControl, 0)`，别指望 `SendToBack()`。
8. **展示元数据与业务契约解耦**：测试断言了 `ITool.Id/Name/Category`，不要为了界面去改接口。新增 `ToolMeta` 映射表按 Id 提供图标/描述/快捷键/六分类归属/配色，未登记工具用兜底值——这样原型视觉升级对插件架构和 81 个测试零侵入。新增工具想上首页卡片，在 `ToolMeta.Map` 登记一条即可（不登记也能用，只是无徽章）。

## 迭代 7 沉淀：三个低成本工具一起加

URL 编解码、时间戳转换、环境变量查看三个工具没有新建项目，而是分别塞进现有的 `WinTools.Tools.Text` / `WinTools.Tools.System`。发现器按 DLL 扫描**所有**带 `[Tool]` 的 `ITool` 类型，一个 DLL 放多个工具完全合法，省去改 sln 与发布拷贝清单。

几条新踩/新确认的坑：

1. **本地函数捕获变量要先声明**：`CreateUI` 里先写 `void SetMode(...)` 再用 `var inputBox = ...`，如果函数体读 `inputBox` 会报 CS0841；先声明变量、再写函数。同理，卡片头 `AddAction` 的 lambda 捕获的集合变量也必须在 `AddAction` 之前赋值，否则 CS0165。
2. **`FluentInput` 没有 `Clear()`**：它是复合 `Panel`，对外只有 `new string Text`；清空要写 `inputBox.Text = string.Empty`，别照抄 `TextBox.Clear()`。
3. **时间类逻辑把时区做成参数**：`TimestampConverter.FromTimestamp/FromDateTime` 都接受可选 `TimeZoneInfo`，单测注入 `Utc` 或固定 `+08:00`，断言不受测试机本地时区影响。
4. **URL 解码别只调 `Uri.UnescapeDataString`**：它对非法 `%` 序列静默留原文。自己按字节扫描（`%XX` → byte，`+` → 空格），再用严格 UTF-8 解码，才能把坏输入变成友好提示，且中文/emoji 往返不失真。
5. **只读系统信息也可以可注入**：环境变量用 `CollectFrom(IDictionary)` 与真实 `Collect()` 分开，单测喂伪造字典即可覆盖排序、跳过空键、null 值、筛选与复制格式。
6. **加一条 CreateUI 冒烟测试很值**：发现机制测试除了验证 Id/Name，再对每个新工具调一次 `CreateUI()`，能在不启窗体的情况下抓出布局构造期的空引用/未赋值捕获。

## 迭代 8 沉淀：网络探测与大目录只读扫描

本轮补齐原 20 个候选清单里最后两个可做的工具（N1 Ping 测试、F4 重复文件查找），顺带加了文本统计、UUID 生成。四个都塞进现有三个工具项目，没有新建 csproj、没有改 sln、没有改宿主。

1. **对象初始化器只能跟在 `new` 后面**：`UiTheme.Input(...) { Dock = ... }` 会报一串 CS1002——那是**方法调用**，不是对象创建表达式。要么先声明再逐项赋值，要么直接 `new FluentInput(...)`。本轮 `Input` / `HintLabel` / `Button` 三处都踩了，症状是中文文案那行附近连报十几个"应输入 ;"，容易误判成引号问题。
2. **先用反射确认枚举成员再写 switch**：`IPStatus` 没有 `BadBufferTooSmall` / `PolicyFailure` 这些"看起来应该有"的成员；写之前用 IDE 补全或查枚举定义，别凭印象。状态文案映射做成纯函数 `Describe(IPStatus)` 后，边界可单测，不必真去制造网络故障。
3. **网络/磁盘操作都通过委托注入**：`PingChecker.RunAsync(target, count, probe, token)` 的 `probe` 由界面层传入真实 `Ping.SendPingAsync`，单测塞假 probe 就能覆盖成功、超时、全失败、取消四条路径。`DuplicateFinder.Find(files, hash, minBytes, token)` 同理——哈希函数注入，单测用临时小文件 + 假哈希，不必造大文件。这是迭代 4"可注入容错"思路的推广：**把外部世界变成参数**。
4. **重复文件查找必须两阶段**：先按文件大小分组，大小唯一的文件根本不可能是副本，直接跳过内容读取；只对同大小组算 SHA-256。大目录扫描的耗时几乎全在 I/O，这一步能省掉绝大多数读取。哈希流式读 + `FileShare.ReadWrite`，被其他程序打开的文件也能读；单个文件失败只跳过它，不让整次扫描崩掉。
5. **只读工具的红线写进报告文案**：F4 只输出"哪几份相同、可释放多少"，界面不提供任何删除/移动按钮，报告标题也写明"只报告不删除"——阶段一"不做什么"边界靠代码与文案双重落实。
6. **测试期望值先算一遍再写**：本轮三个失败全是期望写错（emoji 的 UTF-8 是 4 字节、两个汉字是 3+3 而非 2+3、`FormatSize(2048)` 输出 `2.0 KB` 而非 `2 KB`）。实现没问题的时候，先怀疑测试用例的常量。
